## 1. 坏插件导致 Host 崩溃后的自愈

**状态：已设计（v2 候选，当前只做检测提示，不做自动禁用）**

### 1.1 为什么需要这个

插件把 Host 搞挂之后，**没有任何进程内的代码能执行**——包括本插件自己。
所以这类问题只能在 **Host 之外**解决，这正是本插件 restarter 的形态（`detached: true`）。

### 1.2 现状盘点（哪些已经覆盖）

| 场景 | 后果 | 现有机制 | 需要新做吗 |
|---|---|---|---|
| 插件 import 失败（语法错、依赖缺失） | 该插件 `failed`，**Host 存活** | `reconcileProfile` 的 `contained()` 已兜住异常 | ❌ 不需要 |
| 插件 `apply()` 抛异常 | 同上 | 同上 | ❌ 不需要 |
| **插件运行时崩溃**（`process.exit`、栈溢出） | Host 可能挂 | restarter 能重新拉起，但不知道是谁的锅 | ⚠️ 部分 |
| **插件 OOM / 死循环** | Host 卡死 | 同上 | ⚠️ 部分 |
| Host 反复起不来 | 用户被锁在外面 | **DSH 自带崩溃恢复对话框**（可禁用全部第三方插件 + 备份 patch + 重启） | ❌ DSH 已有 |

**关键结论**：真正缺的不是「禁用能力」（DSH 已有），而是**「知道该禁谁」**。

### 1.3 待定方案：外部看护 + 崩溃计数 + 定向禁用

#### 数据流

```
① 热重载成功后，记录「本次替换了哪些插件」
   → $DSH_HOME/dsh-reload/suspects.json  { at, packages: ['dsh-foo'] }

② 用户点「重启客户端」
   → 杀进程前写检查点
   → restart-checkpoint.json  { attemptAt, healthy: false, suspects: [...] }

③ restarter 拉起新实例（Host 外，不受宿主崩溃影响）

④ 新实例启动，本插件 apply()
   ├─ 5 秒后仍存活 → 写 healthy: true（证明这次启动成功）
   └─ 下次启动读到「有检查点但 healthy !== true」→ 上次启动失败

⑤ 若判定失败：
   ├─ v1：只提示「上次启动失败，可疑插件：X」（不改用户配置）
   └─ v2：提供「一键禁用可疑插件」按钮（走 configEditor）
```

#### 为什么用「启动成功标记」而非「崩溃原因」

Host 崩了之后没有任何代码能执行，**「为什么崩」在进程内不可获得**。
能获得的只有「上次启动有没有走完」。这是看门狗（watchdog）模式的基本前提。

#### v2 禁用实现（用官方 API，不手改 YAML）

```js
const configEditor = ctx.get('configEditor')          // → 见 02-平台事实.md
const entry = configEditor.entries().find((e) => e.options.name === pkgName)
await configEditor.edit(entry, (current) => ({ ...current, disabled: true }))
```

`configEditor.edit` 会「校验 → 持久化 → 走正常 Loader 路径 reconcile」。
底层是 `plugin-manager` 的 `writePluginEnabled()`，它会正确处理
「override 是否冗余」「bundle 层是否已隐含该值」等边角。

### 1.4 三个必须定夺的设计问题

#### 问题 1：禁用范围

| 策略 | 做法 | 风险 | 评价 |
|---|---|---|---|
| **A. 只禁「上次热重载涉及」的插件** | 用 `suspects.json` 记的包名 | 热重载没做过就无嫌疑名单 | ✅ **倾向采用** |
| B. 禁所有第三方插件 | 照抄 DSH 崩溃对话框 | 误伤面太大 | ❌ |
| C. 逐个试 | 每次重启只禁一个 | 安全但要重启多次 | ⭕ 兜底方案 |

**倾向 A**，并加一条约束：**suspects 为空时不禁用任何东西**，只记日志。
理由是「没做过热重载就崩」大概率不是本插件能归因的。

#### 问题 2：自动还是询问

| 方案 | 体验 | 评价 |
|---|---|---|
| 完全自动禁用 | 用户莫名发现插件没了 | ❌ |
| **禁用后明确提示 + 一键恢复** | 用户知情且可撤销 | ✅ 倾向 |
| 只提示不改配置 | 最安全，但要用户自己动手 | ✅ **v1 采用** |

#### 问题 3：会不会误伤本插件自己

**最大风险**：如果 `dsh-reload` 自己有问题，禁用自己会让它消失，提示也弹不出来。

**处理**：suspects 里排除 `dsh-reload` 自身（它已经在跑，说明能加载）。
若排除后 suspects 为空，只记日志不提示。

### 1.5 已识别的风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **误判启动失败** | 启动慢（> 5s）会被误判 | 阈值可配；或改用「首个成功 API 响应」作为信号 |
| **改用户配置** | `configEditor.edit` 会写 `cordis.patch.yml` | 写前备份；v1 不改配置 |
| **禁用循环** | 禁用后还崩 → 再禁一批 → 可能禁光 | 上限：最多禁用 3 个 |
| **自指风险** | 禁用自己则提示无从显示 | 排除自身 |

### 1.6 为什么现在只做 v1（检测 + 提示）

1. **自动改用户配置是高风险动作**，先让用户知情更稳妥
2. **「5 秒判活」是否可靠尚未验证**——需要先在真实崩溃场景里观察
3. 检测机制本身是禁用逻辑的前置，先把数据攒准

### 1.7 实现清单（v1）

| 文件 | 要加什么 |
|---|---|
| `lib/checkpoint.js`（新） | 检查点的写/读/清；`suspects` 的累积与去重 |
| `lib/hot-reload.js` | 重载成功后记录 `suspects` |
| `index.js` | `prepareRestart()` 里写检查点；`apply()` 里挂 5s 定时器标记 healthy |
| `client.js` | 启动时读「上次启动失败」→ toast / 卡片提示 |
| `scripts/` | 新增演练脚本：伪造检查点，验证「失败判定」与「success 覆盖」两条路径 |

## 2. 采纳其他同类插件的设计（调研结论）

**状态：已调研，结论是不采纳**

调研对象：`Monter-code/dsh-live-reload`、`louisyeaaah/dsh-reload`（awesome-dsh-plugin 已收录的同类）。

### 2.1 回滚（把旧模块重新 apply 回去）

**他们的做法**：apply 新模块失败时，`registry.plugin(oldModule, ...)` 把旧模块重新挂回去。

**为什么我们的场景下不适用**：

1. **它解决的是子集问题**：只覆盖「Host 还活着」的情况。而 Host 挂掉时回滚代码根本执行不了
2. **宿主的 `contained()` 已经不崩**：插件 import 失败时 `reconcileProfile` 捕获异常、插件变 `failed`、Host 存活。回滚是在这个已有行为之上再加一层影子模块
3. **要碰私有结构**：`registry.plugin()` 不是公开 API，与本插件「只用公开 API」的设计冲突
4. **有更正确的归口**：Host 真的挂了，应由外部进程（restarter）或 DSH 自带的崩溃恢复处理，而不是 Host 内的插件

**结论**：不采纳。真正的价值归到 §1 的「检测 + 提示」。

### 2.2 缓存诊断（`probeModuleCaches`）

**他们的做法**：把 `loader.internal.loadCache` 的 keys 摊开，排查「报告成功但代码没换」。

**为什么不需要**：他们自己清缓存才需要诊断「清没清掉」。我们走 `reconcileProfile`，
`pending` / `restartReason` 已经如实上报「有没有部分失败」，语义更清楚。

**结论**：不采纳，但记下「若将来出现 `changed=true` 但行为未变」的报告，可回头考虑。

### 2.3 带版本号重新 import（`bust` 兜底）

**他们的做法**：一条缓存都没清掉时，用 `?dshlr=<timestamp>` 强制新模块实例。

**为什么不需要**：这是宿主 `partialReload` 内部的逻辑，`reconcileProfile` 已包含。
重复实现反而可能与宿主行为冲突。

**结论**：不采纳。

### 2.4 值得借鉴的思路（不实现，但影响设计）

| 思路 | 我们怎么吸收 |
|---|---|
| 他们把「缓存键匹配」做得极细（前缀 / realpath / 裸标识符三重） | 提醒我们：`link:` 包在 Windows 上路径有 junction 与 realpath 两种拼写。宿主 `profileRoots` 已经用 `realSpellings()` 处理，**我们不需要自己写，但要理解为何它需要** |
| 他们对「dispose 顺序错了会把 entry 写成 `disabled: true`」有详细记录 | 这解释了为什么**不该自己仿写 reload 序列**——宿主内部有状态耦合，仿真容易踩坑。我们的「只调 `reconcileProfile`」是刻意选择 |

## 3. 已知的差异化边界（写 yml / 对外介绍时用）

**状态：已确认**

本插件的独特处不在「功能多」，而在**形态**：

| 维度 | 本插件 | 同类插件 |
|---|---|---|
| 重载实现 | 调宿主 `hmr.reconcileProfile()` | 自己清模块缓存 + 手动 apply（约 15KB 仿真代码） |
| 宿主内部 API | 不碰 | 大量依赖 `loader.internal`、`registry` |
| 第三方依赖 | 零 | 0–3 个 peerDeps |
| 重启客户端 | ✅ | ❌ 均无 |
| 运行在 Host 外 | ✅ restarter `detached` | ❌ 全在 Host 内 |
| 部分失败的诚实上报 | ✅ `pending` / `restartReason` | ❌ 只能报「清了几个缓存键」 |

**但必须承认：`reconcileProfile` 兜住导入失败这件事是 DSH 原生的**，
所有插件只要正确地调用它都享有这个待遇，**不构成差异化**。
差异化在于「选择调用它」而不是「自己仿真」——这带来的是稳定性与代码量，不是功能。

## 4. 暂不做的功能（已评估，明确搁置）

| 功能 | 为什么不做 |
|---|---|
| **源码目录监听（自动触发重载）** | 「代码改完了」是语义判断，文件系统判断不了。误触发会让插件变 `failed` 且**不可逆**。详见 [04-决策记录.md §2](04-决策记录.md) |
| **智能体触发重启** | 进程拓扑限制：Host 是 Electron 主进程的子进程，杀主进程 = 杀自己，工具响应必丢。详见 [01-设计.md §1.2](01-设计.md) |
| **指定单个插件重载** | 需要调用方先知道「改了哪个」。宿主 `reconcileProfile` 用文件身份判定，不需要这个参数，且能沿 import 图把共享依赖的插件一起带上。加参数只会引入「猜错了」的失败模式 |
| **skill 重载** | DSH 的 skill 按需扫描，改了下次就用，不需要手动刷新。同类插件的 `reload_skill` 解决的是它自建 skill provider 的缓存问题，不是用户的真实痛点 |
| **npm 包版本更新的热重载** | 走 `dsh plugin add` 时 profile 的 `package.json` 变了，DSH 的配置监听会自动 reconcile。不需要本插件介入 |
