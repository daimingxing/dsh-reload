# dsh-reload — 设计定稿

> 需求收敛过程见 [需求对齐.md](需求对齐.md)。

---

## 1. 目标与能力

### 1.1 两个动作

| 动作 | 实现 | 破坏性 | 谁能触发 |
|---|---|---|---|
| **热重载** | `ctx.hmr.runExclusive(() => ctx.hmr.reconcileProfile())` | 低（不碰进程） | 智能体工具 + UI |
| **重启客户端** | detached 外部重启器 → 结束 Electron 主进程 → 等锁释放 → 重新拉起 | **高**（中断所有任务） | **仅 UI** |

### 1.2 明确不做

| 不做 | 理由 |
|---|---|
| 智能体触发重启 | Host 是 Electron 主进程的子进程，智能体跑在 Host 里——杀主进程 = 杀自己，响应必丢 |
| 页面刷新（`location.reload()`） | client bundle 由 `dsh-client-hmr` 500ms 轮询自行替换；Host release 变化时页面自己会提示 |
| 源码目录监听 | 「代码改完了」是语义判断，文件系统判断不了；误触发会让插件变 `failed` 且不可逆 |
| 防抖 / 静默窗 | 没有监听就没有这个问题 |
| 重启失败兜底/回滚 | 第一版不做（用户决定） |
| 修改 profile 配置 | 零配置改动，不动 `hmr`、不动 `root` |

### 1.3 术语

| 术语 | 含义 |
|---|---|
| **热重载** | 不碰进程，把「磁盘上文件变过的插件」停掉、重新 import、重新 apply |
| **在飞任务** | 正在跑的 agent turn / 排队中的 inbox 消息 / 运行中的 job / 打开的 terminal |
| **`link:` 包** | 用 `dsh plugin add link:<路径>` 装的开发中插件 |

## 2. 已核实的平台事实

### 2.1 热重载

| 事实 | 证据 |
|---|---|
| HMR 在桌面 profile 默认启用 | `dsh-base/cordis.patch.yml`：`disabled: !!js "!ctx.get('profileContext')"` |
| `root: []` = 不监听模块源码 | 同上 `config: { root: [] }` |
| `reconcileProfile()` 必须在 `runExclusive()` 内 | 源码抛 `HMR profile reconciliation must run inside runExclusive` |
| `runExclusive` 拒绝嵌套 | 抛 `HMR transactions cannot be nested` |
| 返回值 `{ warnings, pending, restartReason }` | `ProfileReconciliation` |
| `pending[].reason` ∈ `host-module` \| `unmanaged-plugin` \| `module-comparison` | `planReplacement` |
| `restartReason` ∈ `module-comparison` \| `package-moved` | `reconcileProfile` / app-boot |
| 不杀 job / terminal | job 的 owner 是 `sessionId`，terminal 的 owner 是 `Agent`，均不随插件 disposed |
| HMR 不等空闲 | `whenIdle`/`agents`/`jobs` 在 hmr 实现里命中 0 次，直接 `fiber.await()` |
| 只停「文件变了的插件」的 fiber | `planReplacement` → `stopPlanned` |

### 2.2 进程与重启（实测，非推测）

| 事实 | 证据 |
|---|---|
| Host 的 `process.ppid` = Electron 主进程 PID | 实测 `20084 → 4924`；主进程 ppid = explorer |
| `process.execPath` = 桌面 exe | `E:\dsh-desktop\DeepSeek Harness.exe` |
| 主进程 cmdline 无 `--type=` 修饰 | 实测；子进程都有 `--type=gpu-process/renderer/utility` |
| **DSH 进程树不在任何 job object 内** | `NtQueryInformationProcess(h, ProcessJobObjectInformation)` 实测：main 与 host 均为 `NO_JOB`（对照 explorer/pwsh 亦为 `NO_JOB`） |
| **普通 `spawn({detached:true})` 的子进程能存活** | 实测：父进程 `process.exit(0)` 后，detached 子进程 3s 后仍写文件成功 |
| 完整重启链路可行 | 实测：起 restarter → +1210ms 杀主进程 → +1494ms 主进程消失 → +2712ms 拉起新实例 → 新实例运行 ✓ |
| **单实例锁会挡掉过早启动的新实例** | `requestSingleInstanceLock()` 失败即 `quit()` → **必须先等主进程完全消失再启动** |
| `app.relaunch()` 插件够不到 | 仅 `!app.isPackaged` 开发菜单与崩溃恢复对话框可达 |
| `DESKTOP_IPC` 无 restart 通道 | 全表核对 |

> **测量陷阱记录**：`IsProcessInJob(handle, NULL, ...)` 的语义是「与**调用者**是否同一个 job」，
> 不是「是否在任何 job 里」。工具沙箱自身在 job 内时，它会把一切都误报为 `IN_JOB`。
> 正确做法是 `NtQueryInformationProcess` + `ProcessJobObjectInformation`。
> 该误报曾导致「必须用 WMI 才能逃出 job」的错误结论，已更正：**普通 detached spawn 足够。**

### 2.3 在飞任务判据（照抄桌面壳）

```js
// @deepseek-ai/dsh-desktop-host 的 hasDesktopActiveTasks
liveAgents.some(a => a.status === 'running'
                 || a.inbox.nextTurn.length > 0
                 || a.inbox.nextStep.length > 0)
|| [void 0, ...liveAgents].some(a =>
     jobs.list(a?.id).some(j => j.status === 'running' || j.status === 'stopping'))
```

**我们复用同一组判据**，保证与桌面壳自己的「退出前确认」逻辑一致。

## 3. 架构

```
┌────────────────────────── Client（浏览器） ──────────────────────────┐
│  sidebar.footer.action   图标按钮：点击 = 热重载（不弹任何框）        │
│  settings.general.item   一行，两个按钮：热重载 / 重启客户端          │
│         │                                                            │
│         ├─ 热重载 → POST /api/dsh-reload/hot-reload   （直接执行）   │
│         └─ 重启   → GET  /api/dsh-reload/status                     │
│                       ├─ 有在飞任务 → 提示框（只读，无重启按钮）      │
│                       └─ 无在飞任务 → 确认框 → POST /restart         │
└─────────┼────────────────────────────────────────────────────────────┘
          │
┌─────────▼──────────────────── Host ──────────────────────────────────┐
│  路由双挂：connection.fetch（桌面版）+ webServer（Web 版兜底）        │
│                                                                      │
│  hotReload()   ← 唯一实现，工具与 UI 共用                             │
│    hmr.runExclusive(() => hmr.reconcileProfile())                    │
│                                                                      │
│  inspectActivity()  ← 返回在飞任务清单（复用 hasDesktopActiveTasks 判据）│
│                                                                      │
│  restart()     ← 唯一实现，仅 UI 可达                                 │
│    1. 再查一次在飞任务（权威判断，防 TOCTOU）                          │
│    2. 有任务 → 409 + 清单，拒绝执行                                    │
│    3. 无任务 → 写 state.json(pendingRestart)                          │
│              → spawn(detached) 启动 restarter                        │
│              → 立即返回（响应先落地）                                  │
│    4. restarter 等 1.2s → 杀主进程 → 等消失 → 重新拉起                │
│                                                                      │
│  ctx.tools.register('dsh_hot_reload')  ← 只调 hotReload()             │
└──────────────────────────────────────────────────────────────────────┘
```

**原则**：
- `hotReload()` 与 `restart()` 各只有一个实现，工具/UI 共用（遵循 `references/user-actions.md`）
- 重启的**权限判定在 Host 侧**，不信任前端

## 4. 行为规格

### 4.1 热重载

| 触发者 | 行为 |
|---|---|
| 智能体工具 `dsh_hot_reload` | 立即同步执行，返回真实结果 |
| 侧边栏按钮 | 点击立即执行，**不弹任何框**，结果走 toast |
| 设置页「热重载」按钮 | 同上 |

无确认框——因为热重载不碰进程、不杀任务、不丢会话。

### 4.2 重启客户端（核心：安全优先）

**两步判定，Host 侧权威**：

```
用户点「重启」
  ↓
前端 GET /api/dsh-reload/status
  ├─ active = true  → 提示框（只读，见 §4.3），流程结束
  └─ active = false → 确认框 → 用户点「重启」
                        ↓
                     POST /api/dsh-reload/restart
                        ↓
                     Host 再查一次在飞任务（防 TOCTOU）
                       ├─ 有任务 → 409 + 清单 → 前端改用提示框展示
                       └─ 无任务 → 执行重启
```

**关键规则**：只要有在飞任务，**即使用户确认也不会执行重启**。安全优先级高于用户意志。

### 4.3 两个框的区分

| 场景 | 框的类型 | 按钮 | 语义 |
|---|---|---|---|
| **有在飞任务** | **提示框** | 只有「知道了」 | 告知，**没有重启选项** |
| **无在飞任务** | **确认框** | 「重启客户端」/「取消」 | 危险操作二次确认 |

**提示框内容**：

```
现在无法重启

有任务正在运行，重启会中断它们。请等待任务结束后再试。

  会话  「重构登录模块」                      运行中
  任务  pnpm build                             运行中
  终端  dev server                             打开中

                                          [ 知道了 ]
```

**确认框内容**：

```
重启客户端？

DSH 会关闭并自动重新打开。当前没有任务在运行。
重启期间页面会短暂断开，完成后需要重新加载。

                              [ 取消 ]  [ 重启客户端 ]
```

### 4.4 侧边栏按钮

| 交互 | 行为 |
|---|---|
| 点击 | 热重载（不弹框） |
| 悬停 | tooltip「热重载」 |
| 长按 | **无特殊行为**（不做长按重启，见 §10 决策） |

## 5. 接口规格

### 5.1 工具 `dsh_hot_reload`

**参数**：无

**输出**：

```json
{
  "applied": true,
  "changed": true,
  "replacedPlugins": ["dsh-pet", "dsh-reload"],
  "pending": [{ "url": "file:///...", "reason": "host-module" }],
  "restartReason": null,
  "warnings": []
}
```

| 字段 | 说明 |
|---|---|
| `applied` | 操作是否成功完成 |
| `changed` | 是否真有插件被替换（`false` = 磁盘无变化，正常非错误） |
| `replacedPlugins` | 被替换的包名（从 `hmr/reload` 事件收集） |
| `pending` | 需整机重启才生效的模块 |
| `restartReason` | `module-comparison` / `package-moved` / null |
| `warnings` | reconcile 诊断 |

**工具描述要点**：热重载不重启客户端、不中断会话；`pending` 非空需如实告知用户要重启客户端；`changed:false` 不是错误。

### 5.2 HTTP 路由

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/dsh-reload/ping` | 探活 → `{ ok:true, version }` |
| `GET` | `/api/dsh-reload/status` | 在飞任务 → `{ active, agents[], jobs[], terminals[] }` |
| `POST` | `/api/dsh-reload/hot-reload` | 热重载 → 同工具输出 |
| `POST` | `/api/dsh-reload/restart` | 重启；有任务时 409 + 清单 |

**双挂**：`connection.fetch.register`（桌面版主通道）+ `webServer.register({kind:'prefix'})`（Web 兜底）。
Web 兜底用 `ctx.connection.requestRejection(req)` 做同源校验 → 403。

### 5.3 在飞任务的数据结构

```ts
{
  active: boolean,
  agents: [{ id: string, title: string | null, status: 'running' }],
  jobs:   [{ id: string, label: string, status: string }],
  terminals: [{ id: string, title: string }]
}
```

- `agents`：`ctx.agents.list()` 过滤 `status === 'running' || inbox 非空`
- 标题：`ctx.sessionTitle.get(agent.session)` → 取 `title`，无则 null
- `jobs`：`ctx.jobs.list()` 过滤 `running` / `stopping`
- `terminals`：`ctx.terminals.list()`（若可用）

### 5.4 落盘

| 项 | 规格 |
|---|---|
| 路径 | `$DSH_HOME/dsh-reload/state.json` |
| 内容 | `{ version:1, lastHotReload: {...}, pendingRestart: { at, reason } \| null }` |
| 写入 | 原子写（`.tmp` + rename） |
| 用途 | UI 显示上次结果；`pendingRestart` 标记「正在重启」 |

## 6. 重启实现细节

### 6.1 restarter 的启动（普通 detached spawn，无需 WMI）

进程树**不在** job object 内（见 §2.2），所以普通 `spawn({ detached: true })` 即可。

```js
// 用 DSH 自带的 node.exe 跑一个 .mjs 重启器
const nodeExe = join(process.resourcesPath ?? dirname(process.execPath), 'runtime/primary-runtime/dependencies/node/bin/node.exe')
const child = spawn(nodeExe, [restarterPath, JSON.stringify(params)], {
  detached: true,
  stdio: 'ignore',
  windowsHide: true,
})
child.unref()
```

- **无 PowerShell 依赖、无 WMI 依赖**
- 少一层失败面：WMI 服务异常、`Win32_Process.Create` 参数陷阱、PowerShell 引号问题

### 6.2 restarter 脚本逻辑

```js
// 1. 让 HTTP 响应先落地
await sleep(1200)

// 2. 结束主进程
execFileSync('taskkill', ['/PID', String(mainPid), '/F'], { stdio: 'ignore' })

// 3. 轮询直到主进程消失（不用固定 sleep）
for (let i = 0; i < 50; i++) {
  await sleep(200)
  try { process.kill(mainPid, 0) } catch { break }   // 抛错 = 已消失
}

// 4. 清理残留子进程（主进程死时 Host/GPU/renderer 可能变成孤儿）
killLeftovers('DeepSeek Harness.exe', { skipTypes: [], retry: 2 })

// 5. 等待单实例锁释放
await sleep(1200)

// 6. 拉起新实例
spawn(exe, [], { detached: true, stdio: 'ignore', windowsHide: true }).unref()
```

**第 4 步为什么必要**：正常情况 Host 收到 IPC `disconnect` 会主动 shutdown，但**卡死的 Host 会留下孤儿**，占着端口导致新实例启动失败。

**第 5 步是唯一保障**：因为没有 job object 兜底，新实例启动太早会因单实例锁失败而**静默退出**，用户看到的是「DSH 关了，再也没起来」。

### 6.3 时序（实测数据）

```
t=0       Host 写 state.json(pendingRestart) 并返回响应
t=0       spawn(detached) 启动 restarter
t=+1200   restarter 开始 taskkill 主进程
t=+1494   主进程消失
t=+1500   清理残留子进程
t=+2700   拉起新实例
```

- 响应**先返回**（1.2s 缓冲足够前端收到 200）
- 前端收到 200 后显示遮罩，轮询 `/ping`，通了就 `location.reload()`

### 6.4 定位主进程与 exe

```js
const mainPid = process.ppid                    // 已实测等于 Electron 主进程 PID
const exe = process.execPath                    // 已实测等于桌面 exe
```

**安全校验**（防止在 `dsh web` 等非桌面场景误杀终端）：

1. `process.execPath` 的 basename 必须匹配 `/DeepSeek.*Harness/i`
2. 主进程（`process.ppid`）的 cmdline 必须**不含** `--type=`（排除 GPU/renderer/utility 子进程）
3. 任一不满足 → 拒绝重启，返回明确原因

> 这三条来源于 `dsh-hot-restart` 的实践，但**必须自己实现**，不能靠猜测。

### 6.5 为什么不用 `app.relaunch()`

插件拿不到 Electron 主进程的 `app` 对象，`DESKTOP_IPC` 也没有 restart 通道。只能外部重启。

- 两个按钮并排；「重启客户端」用危险色（`--dsw-alias-state-error-primary`）

### 7.4 两个框

自绘 Modal（不 require 宿主 primitives），`role="dialog"` + `aria-modal`，Esc 关闭：

- **提示框**（有任务）：只有「知道了」
- **确认框**（无任务）：「取消」/「重启客户端」

样式只引用 `--dsw-alias-*` token。

### 7.5 重启期间的界面锁定（关键）

**职责**：杀掉主进程前的约 1.2 秒内，窗口仍然存在且可交互，必须封锁全部操作。

**锁定必须在「点击瞬间」开始**，不能等 HTTP 200 回来——POST 往返 + Host 二次查任务可能上百毫秒，
这期间用户完全可能再点一次。

| # | 动作 | 目的 |
|---|---|---|
| 1 | 立刻 `restarting = true` | 状态锁先于网络请求 |
| 2 | 全屏遮罩「正在重启 DSH…」+ `pointer-events` 全捕获 | 挡住所有点击 |
| 3 | 遮罩不可关闭（无按钮、忽略 Esc、忽略点外部） | 防手滑解除 |
| 4 | 所有按钮 disabled（含侧边栏按钮） | 双保险 |
| 5 | 重复点击直接 return | 幂等 |

**遮罩渲染方式：挂 `document.body`（方案 A）**

理由：重启按钮在设置面板里，设置面板 z-index 实测 1000–1100。若用 React 槽位渲染，
遮罩会被困在槽位的层叠上下文内，**盖不住设置面板**，用户仍能操作其他控件。
因此直接创建 `position: fixed; inset: 0; z-index: 12000` 的 DOM 挂到 `document.body`。

> 这偏离了 `practices.md`「不要往 body 追加 DOM」的规则，但同目录的 `dsh-session-recycle`
> 因同样原因（被设置对话框压住）也这么做，并在注释里写明。代码注释必须记录此理由。

### 7.6 锁定解除（必须配对）

**只有「重启真的会发生」才保持锁定。** 否则会让 UI 永久冻结：

| Host 返回 | 前端行为 |
|---|---|
| `200` | **保持锁定**，等窗口消失 |
| `409`（在飞任务冒出来了） | **立刻解锁** → 改显示提示框 |
| `403` / `500` / 网络错误 | **立刻解锁** → toast 报错 |

**超时自动解锁**：锁定后 8 秒若页面仍存活（说明重启未发生），自动解锁并 toast
「重启似乎没有生效，请重试或手动重开 DSH」。

> 这不算「重启失败兜底」——不涉及状态回滚、不写诊断文件、不碰 `state.json`，
> 只是一行 `setTimeout`，用于避免用户面对永久冻结的界面。

### 7.7 重启期间的用户可见时间线

| 时刻 | 发生什么 | 用户看到 |
|---|---|---|
| t=0 | 点「重启客户端」 | 按钮变灰、遮罩升起 |
| t≈50ms | Host 返回 200 | 遮罩「正在重启 DSH…」 |
| **t≈1.2s** | 杀掉主进程 | **整个窗口消失** |
| t≈1.2–2.7s | 桌面空白 | 什么都没有（约 1.5 秒） |
| t≈2.7s | 新实例启动 | **新窗口出现**，加载首页 |
| t≈3s | 插件读到 `pendingRestart` 标记 | toast「DSH 已重启」 |

**不做**：轮询 `/ping`、自动 `location.reload()`。原因：页面在主进程被杀时已随窗口消失，
不存在「一个还活着的页面在等新实例」。

### 7.8 侧边栏按钮

| 交互 | 行为 |

## 8. 错误与边界矩阵

| 情况 | 行为 |
|---|---|
| `ctx.hmr` 不存在 | 工具 `isError`「当前 profile 未启用热重载」；UI 按钮 disabled |
| `reconcileProfile` 抛错 | `applied:false` + 错误消息；红字显示；写 state.json |
| 替换版本加载失败 → 插件 `failed` | 说明「插件 X 加载失败，旧版本已停止；修好后再次热重载即可恢复」 |
| `pending` 非空 | 正常返回，UI 显示「N 个模块需重启客户端才生效」 |
| 并发热重载 | `runExclusive` 天然串行，后到排队 |
| 热重载替换本插件自己 | 结果落盘，UI 轮询拿到；工具响应可能丢（罕见） |
| **重启时有在飞任务** | **拒绝执行**，返回 409 + 清单，前端转提示框 |
| 非桌面环境（`dsh web`） | 重启按钮 disabled，tooltip「仅桌面客户端支持」 |
| exe 名不匹配 / ppid 是子进程 | 拒绝重启，返回具体原因 |
| 新实例启动失败 | **第一版不兜底**（用户决定）。用户看到窗口消失后不再出现，需手动双击图标 |
| 重启请求失败（409/500/网络） | 前端**立刻解锁**并 toast 报错 |
| 锁定时页面仍存活超 8s | 自动解锁 + toast「重启似乎没有生效」 |
| 写 state.json 失败 | 不阻断；console.warn |

## 10. 已确认决策

| 项 | 决策 |
|---|---|
| 包名 | **`dsh-reload`**（npm 可用，已核实 404） |
| 工具名 | `dsh_hot_reload` |
| `/reload` 斜杠命令 | ❌ 不加（智能体用不了斜杠命令） |
| 设置行信息密度 | **最简**：开关 + 说明 + 两个按钮 |
| 侧边栏按钮显示 | 始终显示，但**可在设置里用开关隐藏**（localStorage，立即生效） |
| 侧边栏交互 | 点击 = 热重载；**不做长按重启** |
| 热重载确认框 | ❌ 不加 |
| 重启确认框 | ✅ 有（无任务时） |
| 有任务时点重启 | **提示框，只读，禁止重启**（Host 侧二次校验，防 TOCTOU） |
| 重启期间锁定 | ✅ 点击瞬间即锁，全屏遮罩挂 `document.body`，失败/超时自动解锁 |
| 重启后提示 | ✅ 读 `pendingRestart` 标记 → toast「DSH 已重启」 |
| 重启失败兜底 | ❌ 第一版不做（不做回滚、不写诊断报告） |
| 源码监听 / 静默窗 | ❌ 不做 |
| state.json 历史 | 只存最近一次 |

## 11. 决策记录：讨论过但否决的方案

> 记录所有考虑过、但最终没有采用的方案，避免将来重复讨论，也便于日后复盘。

### 11.1 整机重启的三种实现

| 方案 | 做法 | 否决原因 |
|---|---|---|
| **L3 早期方案：两段式 + 空闲等待 + 续跑 + 回滚** | 排程 → 等所有 agent idle（disarm goal）→ 外部助手 → 重启后 resume 会话 | 复杂度远大于收益；有 goal 的会话永不 idle；做错就是「杀了服务起不来」 |
| **纯 PowerShell `spawn` 助手** | `spawn('pwsh', [...])` 起脚本 | 曾误以为必需（job object 误判），实际普通 detached spawn 就够 |
| **WMI `Win32_Process.Create`** | 用 WMI 创建脱离 job 的进程 | ❌ **已否决**：DSH 进程树根本不在 job object 内（实测 `NO_JOB`），不需要 WMI |
| **采用方案：Node `spawn({detached:true})`** | 用自带 `node.exe` 跑 `.mjs` 重启器 | ✅ 零外部依赖、失败面最小 |

### 11.2 源码目录监听（曾设计，后完全撤销）

| 方案 | 做法 | 否决原因 |
|---|---|---|
| 开启 `hmr` 的 `root: ["."]` | 让 DSH 内置 HMR 监听 profile 目录 | 监听不到 `link:` 包（在 profile 之外），且 `ignored` 含 `**/node_modules`；只剩误触发风险 |
| 本插件自己监听 `linkedRoots` 的 `lib/**/*.js` | debounce 300ms + 静默窗 800ms | ❌ **撤销**：「代码写完了」是语义判断，文件系统判断不了；半成品文件被加载会让插件变 `failed` 且**不可逆**（旧代码不再运行） |
| 静默窗 / debounce 防抖 | 最后一次写入后等 N ms | 撤销监听后一并取消 |
| 自激循环处理（跳过自身目录） | 避免重载自己 | 撤销监听后不存在此问题 |

### 11.3 页面刷新（L2）

| 方案 | 否决原因 |
|---|---|
| `location.reload()` 按钮 | client bundle 由 `dsh-client-hmr` 每 500ms 轮询自行替换，日常不需要；Host release 变化时页面自己会提示并提供刷新按钮 |
| 重启后轮询 `/ping` + 自动 reload | **做不到**：杀掉主进程时窗口一起消失，不存在「活着的页面在等新实例」 |

### 11.4 智能体触发的排程策略

| 策略 | 否决原因 |
|---|---|
| **A：本轮收尾后执行**（曾采用） | 后来改为「立即同步执行」——避免把单次调用变成两步；且它要防的只是「本插件被替换导致响应丢失」这个罕见边角 |
| **B：等所有 agent idle** | 智能体触发时自己正在跑，当场不成立；等到时本轮已结束无法汇报；有 goal 的会话永不 idle；用户发下一条消息又变忙 |
| **C：用户确认** | UI 场景才适用；后简化为「两个按钮（热重载/重启）+ 条件确认框」 |
| **采用方案：立即同步执行** | 返回真实结果，模型拿到即可汇报 |

### 11.5 「稍后」（等空闲）重启

**否决**：job / terminal 归 agent 不归插件，重载不会杀它们；且等空闲不可靠（goal / 新消息）。
改为「有任务就**禁止**重启」的硬策略（安全优先）。

### 11.6 返回「在飞任务清单」给模型

**否决**：无法把任务归因到具体插件（`ModuleFiles.records` 是 hmr 私有字段；job owner 是 sessionId）。
该清单对模型没有可操作性，只是噪音。**但 UI 的提示框需要它**——所以保留在 `inspectActivity()` 里，只给 UI 用。

### 11.7 侧边栏按钮的其他交互

| 方案 | 否决原因 |
|---|---|
| 长按 3 秒 = 重启客户端 | 危险操作藏在隐藏手势里；误触代价高（中断所有任务）；与「热重载无需确认」形成认知冲突 |
| 右键菜单两项 | 可接受但多一步；最终选了更简单的「侧边栏只做热重载，重启放设置页」 |
| 仅当有 `link:` 开发包时显示按钮 | 用户会困惑「为什么时有时无」 |

### 11.8 设置入口的其他位置

| 槽位 | 否决原因 |
|---|---|
| `settings.section`（独立一页） | 用户明确要「通用页最后一行」，不是独立导航页 |
| `plugins.detail.actions` / `plugins.detail.section` | 语境贴合，但用户未选；可作为后续加分项 |
| `conversation.session.header.utilities` | 与第三方插件抢位，窄屏要折叠 |
| `conversation.input.left` / `input.right` | 高频但冲突风险高（`dsh-reset-button` 已占 `input.right`） |
| 托盘菜单 | 托盘在主进程侧，插件够不到 |

### 11.9 侧边栏开关的存储

| 方案 | 否决原因 |
|---|---|
| Host Config（写 `cordis.patch.yml`） | 改一次值要写 profile + 重载插件；纯 UI 偏好不值得 |
| **采用：`localStorage`** | 立即生效、不触发重载、每个浏览器环境独立 |

### 11.10 重启失败兜底

| 方案 | 状态 |
|---|---|
| 自动回滚到上一可用版本 | ❌ 否决：需要备份插件文件；`link:` 包回滚意义不大 |
| 写诊断报告 + 下次启动提示 | ❌ 第一版不做（用户决定） |
| **采用：只做客户端 8 秒超时解锁** | ✅ 不是兜底，只是防止 UI 永久冻结 |

## 12. 实现记录与踩坑

实现已完成并通过 Host 侧验证。以下是过程中真实踩到的问题，**都已修复并加了防护**。

### 12.1 工具 schema 的三个坑（都会导致整个会话报错）

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 安装时报 `JsonSchemaError: schema.properties.applied.required is not supported on type "boolean"` 等 9 条 | `required` 写在了**属性内部**；宿主只接受父级 `required` 数组 | 把 `required` 提到对象层 |
| 2 | 同上，`restartReason.type must be a single type string` | 用了 `type: ['string','null']`，宿主不支持 type 数组 | 改成 `oneOf: [{type:'string'},{type:'null'}]` |
| 3 | **整个会话报「工具的参数结构不符合当前模型要求」** | `parameters: {}` 缺 `type: 'object'`。`tools.register()` 直接收 JSON Schema（不是 `defineTool` 的简写规格），无参工具也必须显式声明 | 改为 `{ type:'object', properties:{}, additionalProperties:false }` |
| 4 | `tool "dsh_hot_reload" returned invalid output: "value.replaced" is not a declared property` | 实现返回了 `replaced`，但 `output.schema` 没声明；输出按 `additionalProperties:false` 校验，多一个字段整个结果被丢弃 | 补上 `replaced` 的声明 |

**防护**：新增 `scripts/check-schema.mjs`，用 **Host 自己的 `assertSupportedJsonSchema`** 校验，并额外比对「实现返回的字段」与「schema 声明的字段」是否完全一致。四个坑都能被它拦住。

### 12.2 状态文件写错位置

| 症状 | 根因 | 修复 |
|---|---|---|
| `state.json` 出现在 `profiles/dsh-reload/` 而不是 `~/.dsh/dsh-reload/` | 兜底逻辑用 `join(profile.dir, '..', 'dsh-reload')`，而 `profiles/desktop/..` 只是 `profiles/`，**少上溯一级** | 优先用 `profileContext.home`（HMR 自己也用它定位 `$DSH_HOME/cordis.patch.yml`）；兜底改为上溯**两**级 |

**证据**：`profileContext` 的已知字段是 `dir / home / patchPath / startedBundles` —— `home` 确实存在，是权威家目录。

### 12.3 槽位组件读不到 props 会整条消失

| 症状 | 根因 | 修复 |
|---|---|---|
| 两个槽位里都看不到本插件的注册 | 组件写成 `function SidebarButton({ t })`，但槽位只传它自己声明的 owner props（`sidebar.footer.action` 传 `{ wide }`，`settings.general.item` 传空）。读 `props.t` 在**首次渲染就抛错**，槽位条目被移除，界面上什么都不出现 | 改为从**闭包**取 `currentT`，组件不接收任何 props |

**防护**：新增 `scripts/check-slot-components.mjs`，检查两个槽位组件的形参必须为空、且体内不出现 `props.`。

### 12.5 为什么 UI 需要刷新页面才能看到

`client-hmr` 只在 bundle 文件元数据变化时推 `rebuilt` 帧；当前页面如果是在插件安装**之前**打开的，它加载的还是旧模块图。刷新一次即可看到侧边栏按钮与设置行。

### 12.6 第五个坑：把「槽位传 t」误判成「槽位不传 t」

| 项 | 内容 |
|---|---|
| 症状 | 槽位注册存在但 `active: false`（条目崩溃），或者界面上完全看不到 |
| 我最初（错误）的判断 | 以为槽位只传自己声明的 owner props（`{ wide }` / 空），组件读 `props.t` 会崩 → 改成模块级 `currentT` 闭包 |
| **实际契约** | 注册选项里的 **`locale: NS` 就是注入翻译函数 `t` 的开关**。宿主自己的代码是：`ctx.slots.inject(slot, () => ctx.slots.register({ name, id, order, locale: NS }, Row))`，而 `function Row({ t })` **从 props 取 t** |
| 正确做法 | 组件从 props 接收 `t`；注册必须带 `locale: NS` |
| 教训 | 判断「某 API 传什么」要以**宿主自己的等价用法**为准，不能从类型签名推断。`Slots.listSubTree` 给出的 `ownerProps` 只列了 owner 自有字段，`t` 是框架统一注入的，不在那份清单里 |

**防护**：`scripts/render-probe.mjs` 用最小 React 替身在 Node 里**真实执行**组件函数体，
并按槽位真实 props（含 `t`）递归渲染整棵 `h()` 树——这类渲染期错误在安装前就能抓到。

### 12.7 为什么 `package.json` 的改动必须重启

实测：改了 `dsh.client.inject` 后，`clientModules` 图里该条目**没有** `inject` 字段。
原因是 DSH 明确限制「仅 `package.json` 变化不被热重载检测」（见 §2.4）。
所以凡是涉及 manifest 的改动（`inject` / `platform` / `exports`），都必须重启一次客户端。
