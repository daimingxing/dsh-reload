# 实现笔记

> 记录开发 dsh-reload 过程中**真实踩到的坑**、排查方法、以及为防止复发而加的校验。
>
> 这些坑大多有共同特征：**报错信息不指向真正的原因**，或者**静默失败没有报错**。
> 所以这份文档的价值不在「记录历史」，而在「下次遇到同样症状能直接定位」。

---

## 1. 工具 schema 的四个坑

这四个都会让**整个会话**出问题，而不只是这个工具不可用。

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | 安装时报 `JsonSchemaError: schema.properties.applied.required is not supported on type "boolean"` 等 9 条 | `required` 写在了**属性内部** | 宿主只接受父级 `required` 数组 |
| 2 | 同上，`restartReason.type must be a single type string` | 用了 `type: ['string','null']` | 宿主不支持 type 数组，改用 `oneOf` |
| 3 | **整个会话报「工具的参数结构不符合当前模型要求，被服务端拒绝」** | `parameters: {}` 缺 `type: 'object'` | 见下 §1.1 |
| 4 | `tool "dsh_hot_reload" returned invalid output: "value.replaced" is not a declared property` | 实现返回了 `replaced`，但 `output.schema` 没声明 | 输出按 `additionalProperties:false` 校验，**多一个字段整个结果被丢弃** |

### 1.1 `tools.register()` 收的是完整 JSON Schema

宿主有**两套**不同的入参形式：

| API | 入参 |
|---|---|
| `defineTool({ parameters: { x: { type: 'string' } } })` | 简写规格，内部编译成 JSON Schema |
| `ctx.tools.register({ parameters })` | **已经是完整 JSON Schema** |

无参工具也必须显式写：

```js
parameters: { type: 'object', properties: {}, additionalProperties: false }
```

写成 `{}` 会一路通过注册，直到**组装工具列表发给模型时**才被服务端拒绝——
错误指向「参数结构不符合当前模型要求」，看起来像模型的问题，实际是插件的问题。

### 1.2 宿主支持的 JSON Schema 子集

`type / oneOf / properties / required / additionalProperties / items / enum / const`
\+ 注解（`description` / `title` / `default` / `examples`）。

**不支持**：`type` 数组、`allOf` / `anyOf` / `not`、`pattern`、数值范围等。

### 1.3 防护：`scripts/check-schema.mjs`

用**宿主自己的 `assertSupportedJsonSchema`** 校验，并额外比对
「`hotReload()` 返回的字段」与「`output.schema` 声明的字段」是否完全一致。

```sh
ELECTRON_RUN_AS_NODE=1 "<DeepSeek Harness.exe>" --expose-internals scripts/check-schema.mjs
```

四个坑都能被它拦住。**四个坑之外还拦住了第 4 类**（字段不一致），那是最隐蔽的一类。

## 2. 状态文件写错位置

| 项 | 内容 |
|---|---|
| 症状 | `state.json` 出现在 `profiles/dsh-reload/` 而不是 `~/.dsh/dsh-reload/` |
| 根因 | 兜底逻辑写 `join(profile.dir, '..', 'dsh-reload')`，而 `profiles/desktop/..` 只是 `profiles/`，**少上溯一级** |
| 修复 | 优先用 `profileContext.home`（权威家目录），兜底改为上溯**两**级 |

`profileContext` 的已知字段：`dir / home / patchPath / startedBundles` —— `home` 确实存在，
HMR 自己也用它来定位 `$DSH_HOME/cordis.patch.yml`。

**教训**：路径推导不要靠猜层级。找一个「宿主自己就在用」的同源字段。

## 3. 槽位注册了但界面上看不到

这是**最耗时的一个坑**，前后误判过两次。

### 3.1 症状与诊断线索

| 症状 | 含义 |
|---|---|
| `Slots.listSubTree` 里能看到自己的 occupant，但 `active: false` | 注册成功，**渲染时抛错**，条目被移除 |
| 连 occupant 都看不到 | 模块根本没执行到 `apply`，或注册被拒 |

两个症状原因不同，先分清再查。

### 3.2 误判一：以为是 `props` 的问题（方向反了）

我最初看到 `ownerProps` 只有 `{ wide }` / 空，判断「组件不能读 `props.t`」，
于是改成模块级闭包 `currentT`。

**实际正好相反**：注册选项里的 `locale: NS` 就是注入 `t` 的开关，
宿主自己的组件正是 `function CurrentVersionRow({ t })` 从 props 取。

**教训**：判断「某 API 传什么」，要以**宿主自己的等价用法**为准，
不能从类型签名或 Inspect 输出的字段清单推断。`ownerProps` 只列 owner 自有字段。

### 3.3 误判二：漏了 `dsh.client.inject`

`package.json` 的 `dsh.client` 少了 `inject`。补上后仍不生效——因为
**`package.json` 的改动不会被热重载读取**，必须重启客户端。

### 3.4 真正的错误：裸 `t(` 未定义

第一次 `active: false` 的真正原因是：批量替换 `t(` → `currentT(` 时漏了几处，
组件渲染时抛 `ReferenceError: t is not defined`。

**这个错误在浏览器里只表现为「槽位条目消失」，Console 里没有明显红字。**

### 3.5 防护：两个脚本

**`scripts/render-probe.mjs`** —— 最有用的一个。用最小 React 替身在 Node 里
**真实执行**组件函数体，并按槽位真实 props（含 `t`）**递归渲染整棵 `h()` 树**：

```sh
node scripts/render-probe.mjs
```

输出会告诉你每个槽位注册成什么 id、渲染出多少个节点。上面那个
`t is not defined` 它一跑就抓到了。

**`scripts/check-slot-components.mjs`** —— 按宿主契约做静态审查：
`inject`/`register` 成对、注册带 `locale: NS`、组件形参接收 `t`。

> 注意：这个脚本最初写的是「槽位组件不得读 props」——**规则本身就是错的**，
> 会误伤正确写法。已在发现误判后重写。

## 4. `changed: false` 不一定意味着有 bug

改了 `client.js` 后调用 `dsh_hot_reload`，返回「没有检测到改动」。这不是 bug：

- 本插件的 `changed` 由 **Host 的 fiber uid 前后快照**判定
- `client.js` 是 Client 半，由 `dsh-client-hmr` 的轮询独立替换，**不经过 Host 的 fiber 比较**

所以「改了 Client 文件但工具说没变化」是**正确行为**。

判断 Client 改动是否生效，看这个：

```sh
curl -s "http://127.0.0.1:<port>/plugins/events" -H "accept: text/event-stream" \
  | grep -o '{"id":"dsh-reload"[^}]*}'
```

返回的条目里有 `rev` 和 `inject` —— `rev` 变了说明 bundle 已更新，
`inject` 出现说明 manifest 被重新读取过（即重启过）。

## 5. 快速自检清单

改完代码后按顺序跑，能拦住绝大多数回归：

```sh
# 1. 语法
node --check index.js && node --check client.js && \
  for f in lib/*.js lib/*.mjs; do node --check "$f"; done

# 2. 工具 schema（用宿主自己的断言函数）
ELECTRON_RUN_AS_NODE=1 "<DeepSeek Harness.exe>" --expose-internals scripts/check-schema.mjs

# 3. 槽位注册写法
node scripts/check-slot-components.mjs

# 4. 组件能否真实渲染（能抓渲染期异常）
node scripts/render-probe.mjs

# 5. 声明与路径
node scripts/inspect-graph.mjs

# 6. 重启链路（用假主进程，不影响正在运行的 DSH）
node scripts/restarter-drill.mjs

# 7. profileContext 字段与 stateDir 落点（排查「状态文件写错位置」）
ELECTRON_RUN_AS_NODE=1 "<DeepSeek Harness.exe>" scripts/check-paths.mjs
```

> 需要 Host 运行时的脚本会自己探测安装位置（见 `scripts/lib/runtime.mjs`），
> 装在非默认路径时用 `DSH_RUNTIME_DIR` 指定 dsh 包根目录即可。

| 脚本 | 检查什么 | 何时必须跑 |
|---|---|---|
| `check-schema.mjs` | 工具 schema 合法性 + 实现字段与声明字段一致 | 改了工具定义 |
| `check-slot-components.mjs` | 槽位注册写法符合宿主契约（含 keyed 槽位的 key） | 改了槽位注册 |
| `render-probe.mjs` | 组件能否真实渲染（抓渲染期异常） | 改了 UI 组件 |
| `inspect-graph.mjs` | 声明与路径一致性 | 改了 `package.json` |
| `restarter-drill.mjs` | 重启链路：存活探测、环境剥离、重试 | 改了重启逻辑 |
| `check-paths.mjs` | `profileContext` 字段 + `stateDir()` 最终落点 | 状态文件位置可疑时（见 §2） |

> `check-schema.mjs` 与 `render-probe.mjs` 是最值得跑的两个：
> 前者拦住四类 schema 错误，后者拦住「界面上什么都没有」的渲染期异常。

## 7. 「重启后客户端关掉、不再打开」

这是**静默失败**的典型：日志看起来一切正常，用户看到的是 DSH 消失了。

### 7.1 症状与误导性证据

| 证据 | 看起来的含义 | 实际含义 |
|---|---|---|
| `restart.log` 有「新实例已启动 pid=36184」 | 拉起来了 | 只是 `spawn()` 返回了 PID |
| `restart-done.txt` 有内容 | 重启流程走完了 | restarter 正常收尾，不代表客户端活着 |
| `spawn()` 不抛异常 | 成功了 | Electron 秒退也是 exit 0 |
| `taskkill` 之后主进程确实消失 | 前半段正常 | 前半段本来就正常 |

**教训**：这条链路里「进程起来了」和「进程活下来了」是两件事，
`spawn()` 的返回值无法区分。

### 7.2 根因

Host 进程的环境里有 `ELECTRON_RUN_AS_NODE=1`（桌面壳 `desktopNodeEnvironment()`
主动加的，因为它要用同一个 exe 当 node 跑 Host）。restarter 继承这个环境，
拉起新实例时又原样传下去 → 新实例变成**纯 Node 进程**，不建窗口，无参数时
立刻以 0 退出。

一行验证：

```sh
ELECTRON_RUN_AS_NODE=1 "<exe>" --version   # → v24.21.0   ← Node 模式
                "<exe>" --version          # → （应用模式）
```

### 7.3 修复

1. `lib/restart.js` 的 `desktopLaunchEnv()`：拉起新实例前删掉
   `ELECTRON_RUN_AS_NODE` / `ELECTRON_NO_ATTACH_CONSOLE` / `ELECTRON_ENABLE_LOGGING`，
   保留其余用户环境。**不要** `{...process.env}`。
2. `lib/restart.js` 的 `launchDesktopAndVerify()`：拉起后观察约 2s，进程还在才算成功。
3. `lib/restarter.mjs`：失败重试最多 3 次（单实例锁释放有延迟），全失败则
   写日志并抛错，让「重启失败」在日志里是显式的。

### 7.4 防护：`scripts/restarter-drill.mjs`

```sh
node scripts/restarter-drill.mjs
```

四条检查，全程**不碰正在运行的 DSH**：

| # | 检查 | 做法 |
|---|---|---|
| 1 | 短命进程被判「未存活」 | 拉起 `node -e 'process.exit(0)'`，期望返回 null |
| 2 | 常驻进程被判「存活」 | 拉起 sleep 进程，期望返回 PID |
| 3 | 环境剥离 | 断言三个 Electron 变量被删、用户变量保留、入参未被改 |
| 4 | restarter 全链路 | 用假主进程走完「杀 → 拉起 → 探测 → 重试 → 报错」，断言日志 |

> 第 4 步用**假主进程**是关键：真实 DSH 正在运行，杀它会把当前会话一起带走。
> 而新实例会被**单实例锁**挡掉——这正好让「拉起后秒退」这条分支被真实覆盖。

### 7.5 ⚠️ 演练脚本曾经真的会关掉用户的 DSH

**症状**：每次跑完验证，用户的 DSH 就无故关闭（「dsh 自己崩溃了，经常发生」）。

**根因**：`restarter.mjs` 的 `killLeftovers()` 执行
`taskkill /IM "DeepSeek Harness.exe" /F` —— **按镜像名杀所有同名进程**。
演练脚本最初把**真实的桌面 exe 路径**写进 config，于是跑一次演练 =
强制关掉用户正在用的 DSH。而 `spawn()` 不报错、退出码正常，所以看起来「莫名崩溃」。

**修复**：

1. `restarter.mjs` 的 `killLeftovers()` 增加演练开关：
   读到 `DSH_RELOAD_DRILL=1` 就跳过按镜像名清理。
2. `restarter-drill.mjs` 不再出现真实 exe 路径：`exe` 一律传 `node.exe` 替身，
   并以 `DSH_RELOAD_DRILL=1` 启动 restarter。

**教训（很重要）**：写「验证脚本」时，**任何按名字杀进程 / 按名字匹配资源的操作
都必须先问「这个操作会不会波及用户正在用的东西」**。
本项目的 restarter 在生产环境里按镜像名清理是对的（单实例应用，旧的全清掉），
但同一个函数被测试复用时就是灾难。

**验证方式**：跑演练前后各数一次 `DeepSeek Harness` 进程数，必须不变。

### 7.6 蒙版「看不见」：主题 token 用错了

**症状**：点「重启客户端」后界面没有任何变化，看不到蒙版。

**根因**：遮罩背景用了 `--dsw-alias-bg-base`。这个 token 的语义是
**「应用基础背景色」（不透明的页面底色）**，深色主题下是
`--dsw-static-neutral-bluish-950`（近黑）——**跟页面背景同色**，
盖上去等于没盖。

**正确的 token**：`--dsw-alias-bg-mask-1`（深色 `#00000080`、浅色 `#0000003d`），
这才是「半透明遮罩色」。设置面板自己的 mask 也用它。

**顺带修的两点**：

- 遮罩中央的文字放进 `.dshr-lock-card`（有底色 + 边框 + 阴影），
  否则浅色主题下白字压在浅色遮罩上会糊。
- 加 `.dshr-lock-spinner` 转圈指示器：光有文字会让人怀疑「是不是卡住了」。

**教训**：用主题 token 前先看它的 `description` 与**实际值**。
`Theme.listTokens` 只给名字和类型，值要读 `dsh-client-ui-theme` 的 CSS。
名字里带 `bg-base` 的不一定是「遮罩」，`mask` 才是。

### 7.7 toast 位置

toast 从 `bottom: 28px` 改到顶部：

```css
top: calc(var(--dsh-frame-chrome-top, 0px) + 16px);
```

底部会跟输入框、状态栏挤在一起。`--dsh-frame-chrome-top` 是宿主自己的
窗口标题栏高度变量（设置面板的 mask 也用它），加上它才不会被标题栏压住。

### 7.8 模板字符串里不能出现反引号

改 CSS 注释时用了 `` `--dsw-alias-bg-mask-*` `` 这种 markdown 行内代码写法，
**反引号直接终止了 `const STYLE = \`...\`` 模板字符串**，报错却是
`Invalid left-hand side expression in postfix operation`（指向 `const STYLE = `），
完全看不出真正原因。

**规则**：`STYLE` 模板字符串内部（包括 CSS 注释）**不要写反引号**。
