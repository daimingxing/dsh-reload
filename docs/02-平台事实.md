## 1. 热重载（`@deepseek-ai/dsh-hmr`）

### 1.1 服务与调用约束

| 事实 | 证据 |
|---|---|
| 提供 `ctx.hmr` 服务 | `dsh-hmr/lib/index.js` |
| `runExclusive` 是 AsyncLocalStorage 串行队列，**禁止嵌套** | 抛 `HMR transactions cannot be nested` |
| `reconcileProfile()` **必须在 `runExclusive()` 内** | 抛 `HMR profile reconciliation must run inside runExclusive` |
| 返回 `{ warnings, pending, restartReason }` | `ProfileReconciliation` 类型 |

### 1.2 `reconcileProfile()` 做了什么

1. 用**临时标记文件的 mtime** 作比较基准（`files.now()`）
2. 比较范围 = profile 目录 + `node_modules` 下**所有符号链接的目标**（`profileRoots`）
3. 比较键 = `inode:size:mtimeMs`（`identityOf`）
4. `planReplacement`（L1214）对每个陈旧模块分类：
   - 落在 host 静态依赖图 → `pending[{reason:'host-module'}]`，保持运行
   - 非 Loader entry 的插件 → `pending[{reason:'unmanaged-plugin'}]`
   - 其余 → evict（L1157 清 ESM `loadCache` + CJS `require.cache`）
5. `stopPlanned`（L1274）：manifest 失效、evict、`registry.delete`、`fiber.await`
6. app-boot `recomposeProfile`（L3782）重启 entry

### 1.3 `restartReason` 只有两种

| 值 | 来源 |
|---|---|
| `'module-comparison'` | 比较失败或无 ESM cache（L1363） |
| `'package-moved'` | app-boot 的 `ResolutionRestartRequired`（L3840-3845） |

`pluginManager` 上报的是 `restartReason ?? pending[0].reason`（L2367）。

### 1.4 HMR **不等空闲**

`whenIdle` / `agents` / `jobs` 在 hmr 与 plugin-manager 的实现里命中 **0 次**，
直接 `fiber.await()`。后果见 [01-设计.md §3.1](01-设计.md)。

### 1.5 启用状态

```yaml
# dsh-base/cordis.patch.yml
- id: hmr
  name: '@deepseek-ai/dsh-hmr'
  disabled: !!js "!ctx.get('profileContext')"
  config:
    root: []
```

桌面端有 profileContext → **默认启用**；`root: []` 表示**不监听模块源码目录**。

### 1.6 `reconcileProfile` 不会触发 `hmr/reload` 事件

`hmr/reload` 只在 `partialReload()`（**源码文件监听**路径）里 `emit`。
`reconcileProfile` 走的是 app-boot 的 recompose 路径，不发这个事件。

**这就是本插件用「fiber uid 前后快照」而不是听事件来判断哪些插件被替换的原因。**

## 2. 三套「自动刷新」，别搞混

| 监听 | 监听对象 | 默认状态 | 触发后 |
|---|---|---|---|
| **配置监听**（`watchConfig`，chokidar） | profile 的 `cordis.patch.yml` + `$DSH_HOME/cordis.patch.yml` + profile `package.json` | **常开** | `reconcileProfile()` |
| **模块源码监听**（`config.root`，chokidar） | `baseDir`（= profile 目录）下的 glob，`ignored` 默认含 `**/node_modules` | **关闭**（`root: []`） | `partialReload()` |
| **client bundle 轮询**（`dsh-client-hmr`） | 各包 `lib/client.js` 的 `mtime/ctime/size` | **常开** | SSE 推 `rebuilt` → 浏览器就地替换 |

**「新加插件自动出现」是配置监听的效果**（profile `package.json` 的 bundles 列表变了）。

### 2.1 `root: ["."]` 为什么监听不到插件源码

```js
this.baseDir = fileURLToPath(new URL(config.base || ".", ctx.baseUrl))
```

`ctx.baseUrl` 是 **profile 目录**；`link:` 开发包的目标在 profile 目录**之外**，
不在 watch 范围；即使在内，`ignored` 也含 `**/node_modules`。

### 2.2 那 `link:` 包的改动靠什么生效

**靠 `reconcileProfile` 里的文件比较，与 watcher 无关。**

```js
// 比较范围 = profile 目录 + node_modules 下所有符号链接的目标
function profileRoots(dir) {
  const linked = readdirSync(modules).flatMap(...).filter(p => lstatSync(p).isSymbolicLink())
  return [dir, ...linked].map(root => root + sep)
}
// 比较键 = inode : size : mtimeMs
key: `${stats.ino}:${stats.size}:${stats.mtimeMs}`
```

官方 README 原话：「……会在下一次此类重新组合时生效，无需重启；**不要求通过 root 监听源码**。」

**缺的只是「什么时候调用」这个触发器** —— 这正是本插件提供的东西。

## 3. 桌面进程与重启

### 3.1 进程拓扑（实测）

```
DeepSeek Harness.exe            ← Electron 主进程，ppid = explorer
├── --type=gpu-process
├── --type=utility (network / audio)
├── --type=renderer
└── --expose-internals .../dsh-desktop-host/lib/index.js   ← Host，ppid = 主进程
    └── .../dsh-subprocess-local/lib/runner.js             ← 工具子进程
```

| 事实 | 证据 |
|---|---|
| Host 的 `process.ppid` = Electron 主进程 PID | 实测 `20084 → 4924` |
| `process.execPath` = 桌面 exe | `E:\dsh-desktop\DeepSeek Harness.exe` |
| 主进程 cmdline 无 `--type=` 修饰 | 实测；所有子进程都有 |
| **DSH 进程树不在任何 job object 内** | 见 §3.2 |
| **普通 `spawn({detached:true})` 的子进程能存活** | 实测：父进程 `process.exit(0)` 后，detached 子进程 3s 后仍写文件成功 |
| 完整重启链路可行 | 实测：起 restarter → +1210ms 杀主进程 → +1494ms 主进程消失 → +2712ms 拉起新实例 → 新实例运行 ✓ |
| 单实例锁会挡掉过早启动的新实例 | `requestSingleInstanceLock()` 失败即 `quit()` |
| **Host 环境带 `ELECTRON_RUN_AS_NODE=1`** | 见 §3.2.1；原样传给新实例会让它以纯 Node 模式秒退 |
| `app.relaunch()` 插件够不到 | 仅 `!app.isPackaged` 开发菜单与崩溃恢复对话框可达 |
| `DESKTOP_IPC` 无 restart 通道 | 全表核对；`createProductApi()` 只有 `browser / deviceInfo / keyboard / shortcuts / updates` |

### 3.2 关于 job object 的测量陷阱（重要）

**`IsProcessInJob(handle, NULL, &result)` 的语义是「该进程与调用者是否同一个 job」，不是「是否在任何 job 里」。**

工具沙箱自身在 job 内时，它会把一切都误报为 `IN_JOB`。
正确做法是 `NtQueryInformationProcess(h, ProcessJobObjectInformation)`：

```csharp
IntPtr job = IntPtr.Zero;
NtQueryInformationProcess(h, 47 /* ProcessJobObjectInformation */, ref job, IntPtr.Size, out _);
// job == IntPtr.Zero → 不属于任何 job
```

实测对照（explorer 与 pwsh 均为 `NO_JOB`，说明测量方法可信）：

| 进程 | 结论 |
|---|---|
| explorer | `NO_JOB` |
| pwsh（工具沙箱） | `NO_JOB` |
| DSH main | `NO_JOB` |
| DSH host | `NO_JOB` |

**这个误报曾导致「必须用 WMI 才能逃出 job」的错误结论。更正后：普通 detached spawn 足够，无需 WMI / PowerShell。**

### 3.2.1 `ELECTRON_RUN_AS_NODE` 会「吃掉」重新拉起的客户端（重要）

这是「点重启后客户端关掉、却不再打开」的**根因**。

桌面壳拉起 Host 时用的是 `desktopNodeEnvironment()`（`lib/main.js` L3649），它给
子进程环境显式加上：

```js
function desktopNodeEnvironment(executable, bin, environment) {
  return { ...environment, ELECTRON_RUN_AS_NODE: '1', ... }
}
```

于是 **Host 进程的环境里始终带着 `ELECTRON_RUN_AS_NODE=1`**。重启器是 Host 的
子进程，会继承它；如果拉起新实例时原样传下去，Electron 就会把新实例当成**纯
Node 进程**跑——不建窗口，无参数时立刻以 0 退出。

实测（同一个 exe，只差这个环境变量）：

```sh
ELECTRON_RUN_AS_NODE=1 "<exe>" --version   # → v24.21.0   （Node 模式，exit 0）
                "<exe>" --version          # → （应用模式，无输出）
```

**关键点：这是静默失败。** `spawn()` 不抛错，`exitCode` 是 0，日志里看着
「新实例已启动 pid=xxxx」——用户看到的却是「DSH 关了没再开」。

**修复**：拉起新实例前剥离 `ELECTRON_RUN_AS_NODE`（以及 `ELECTRON_NO_ATTACH_CONSOLE`、
`ELECTRON_ENABLE_LOGGING` 这类桌面壳给 Host 设的调试开关），见 `lib/restart.js`
的 `desktopLaunchEnv()`。**不要**直接 `{...process.env}`。

**并且必须做存活探测**：拉起后观察约 2s，进程还在才算成功。单靠 `spawn()`
的返回值无法区分「起来了」和「起来后秒退」。

### 3.3 桌面壳的优雅退出链路

- `app.quit()` → `before-quit` preventDefault → `quitConfirmation.confirm()` →
  `host.inspectQuit()`（返回 `activeTasks` / `scheduledTasks`）→ 有任务弹原生框 → `finishQuit()`
- `host.stop()`：发 `{type:'shutdown'}` → 等 10s → SIGTERM → 再 5s → SIGKILL
- 关窗 = 隐藏到托盘（首次弹提示）；托盘菜单「退出」→ `app.quit()`

### 3.4 在飞任务判据（照抄桌面壳）

```js
// @deepseek-ai/dsh-desktop-host 的 hasDesktopActiveTasks
liveAgents.some(a => a.status === 'running'
                 || a.inbox.nextTurn.length > 0
                 || a.inbox.nextStep.length > 0)
|| [void 0, ...liveAgents].some(a =>
     jobs.list(a?.id).some(j => j.status === 'running' || j.status === 'stopping'))
```

`[void 0, ...liveAgents]` 里的 `void 0` 不能省：它让 `jobs.list(undefined)` 也参与查询，
覆盖「不属于任何会话的全局 job」。

**任务不归插件所有**：job 的 owner 是 `sessionId`，terminal 的 owner 是 `Agent`。
所以「哪些任务在使用某个插件」这个问题**在 DSH 里无法回答**——本插件只报「在飞任务清单」。

## 4. 客户端

### 4.1 client bundle 的替换机制

`dsh-client-hmr` host 侧轮询每个包 `lib/client.js` 的 `mtime/ctime/size` 作为 revision，
变化时通过 `/plugins/events` SSE 推 `{type:'rebuilt'|'graph'}`；
浏览器侧 `entries.reload(id, rev)` 就地替换，**不需要 `location.reload()`**。

仅 Host release（版本/commit）变化时 `ReleaseChangeGate` 会阻断，此时页面自己会提示并提供刷新按钮。

### 4.2 `dsh.client` 声明

```json
"dsh": {
  "bundle": { "patch": "./cordis.patch.yml" },
  "client": {
    "platform": "web",
    "immediately": true,
    "inject": ["@deepseek-ai/dsh-client-ui-sidebar", "..."]
  }
}
```

| 字段 | 说明 |
|---|---|
| `platform` | 必须是 `"web"`；其他值该包不进入 client 图 |
| `exports["./client"]` | 必须是字符串或 `{ default: string }`；缺了会抛错 |
| `inject` | 只用于**激活顺序**，不影响能否工作 |
| `immediately` | 立即激活，不等首次需要 |

**`package.json` 的改动不会热重载**（DSH 明确限制），涉及 manifest 的改动必须重启。

### 4.3 槽位与 `t` 的注入

注册写法（宿主自己的等价用法）：

```js
ctx.slots.inject('settings.general.item', () => ctx.slots.register({
  name: 'settings.general.item', id: 'current-version', order: 100, locale: NS,
}, CurrentVersionRow))

function CurrentVersionRow({ t }) {    // ← 从 props 取 t
  return h('div', null, t('general.currentVersion', { version: '0.2.1-rc.3' }))
}
```

**`locale: NS` 就是框架注入翻译函数 `t` 的开关。**
`Slots.listSubTree` 给出的 `ownerProps` 只列 owner 自有字段（如 `{ wide }`），
`t` 是框架统一注入的，**不在那份清单里** —— 不要据此判断「槽位不传 t」。

### 4.3.1 插件详情页的两个槽位

插件管理页（`@deepseek-ai/dsh-client-ui-plugin-manager`）给每个插件留了两个
可以放自己内容的位置：

| 槽位 | kind | 注册时给什么 | 渲染条件 |
|---|---|---|---|
| `plugins.bundle.config` | keyed | `key: <包名>` | 仅当 `ledger.bundles.has(pkg.name)` 为真，即**这个 key 集合里有该包名** |
| `plugins.detail.section` | list | `id` + `order` | 总是渲染，组件自己对 `subject` 返回 null 表示无关 |

`plugins.bundle.config` 的实际渲染点（`lib/client.js` L2964）：

```js
configured ? renderSlot('plugins.bundle.config', { view: 'page' }, { entryKey: pkg.name }) : null
```

两条硬约束，写错都是**静默不显示、无报错**：

1. **`key` 必须精确等于包名**，不是 Loader entry id。
   `configured` 来自 `ledger.bundles.has(openPkg.name)`，而 `ledger.bundles` 就是
   该槽位上注册过的 key 集合。`dsh-connect-workbuddy` 因此同时注册
   `dsh-connect-workbuddy` 与 `include:dsh-connect-workbuddy` 两个 key（issue #55）。
2. **owner props 是 `{ view, form? }`**。`view: 'summary'` 时宿主只取一行摘要；
   `view: 'page'` 才是完整卡片。`form` 只有 bundle 声明了 Host Config 时才存在。

`plugins.detail.section` 的 owner props 是 `{ subject }`，`subject` 形如
`{ kind: 'bundle', pkg: {...} }`（另有 row / item 两种 kind）。

### 4.3.2 设置面板的结构与可用槽位

设置面板由 `@deepseek-ai/dsh-client-ui-settings-general` 的 `SettingsPanel` 渲染，
结构固定：

```
.content
├── .header  (54px 高, padding 20px 14px 8px 10px)
│   ├── .actions   ← renderSlot('settings.action')   flex-end, gap 8px
│   └── .close     ← 28×28 关闭按钮
└── .options
    └── renderSlot('settings.section', { close }, { only: activeId })  ← 按 id 挂整页
```

| 槽位 | kind / scope | 能放什么 |
|---|---|---|
| `settings.action` | list / **root** | 顶栏右侧（Close 左边）的按钮。**任何设置页都渲染** |
| `settings.section` | list / root | 一整个设置页（导航项 + 内容） |
| `settings.general.item` | list / root | 「通用」页里的一行偏好 |
| `settings.header` | single / root | 面板标题文字（`shadows-shipped-ui`） |

**关键事实：「账户与余额」页没有任何子槽位。**
`dsh-client-ui-settings-account` 的 `AccountSection` 里 **`renderSlot` 出现 0 次** ——
那个页面的 DOM 是宿主自己写死的，页面内部（包括「最下方」）没有扩展点。
所以想在该页底部放东西，只有两条路：挂 `settings.action`（顶栏，官方），
或者用 DOM 定位 hack（会随宿主 CSS 变化而失效）。

`settings.action` 的尺寸约束来自 `.header`（54px）与 `.close`（28×28），
放进去的控件应控制在 28px 高，否则会撑高顶栏。

### 4.3.3 主界面可放按钮的位置（非设置区域）

实测自 `Slots.listSubTree` + 宿主源码。**root scope 且当前可用的**：

| 槽位 | kind/scope | 位置 | 占用 | replaceRisk |
|---|---|---|---|---|
| `shell.overlay` | list / **root** | 整窗浮层，可自由定位 | 16 个（全是 toast / 浮层） | none |
| `sidebar.panellist.actions` | list / **root** | 侧边栏「更多」菜单的行 | `entry-customization` | none |
| `conversation.header.leading` | single / **root** | 主区域顶栏最左，会话标题左边 | **空** | none |
| `conversation.input.right` | list / session | 提交按钮前 | 空 | none |
| `conversation.hero.options` | list / session | 新会话空态选项行 | 空 | none |

> `conversation.header.leading` 技术上可用（root、无占用、无会话时也在），
> 但**本插件最终没有用它**：用户判断热重载按钮不该占会话标题旁边那个位置。
> 记在这里是为了避免将来重复调研。

尺寸事实：

| 项 | 值（来源：`dsh-client-ui-conversation` 的 `ConversationRoot` CSS） |
|---|---|
| `.header` | grid `auto minmax(0,1fr)`，`min-height:76px`，`padding:10px 28px 0 20px` |
| `.headerLeading` | `flex:none; gap:8px`（顶栏第一列） |
| `.headerActions` | `flex:none; gap:8px` |
| `.headerUtilities` | `flex:none; gap:8px; margin-left:20px` |
| `.headerCorner` | `margin-left:8px; margin-right:-16px` |
| `shell.overlay` 层 | `pointer-events: none`；**占用者必须自己 `auto` 回来，否则点不到** |
| 「更多」菜单 | `width:288px`（`sidebar` 的 `.moreMenu`） |

**不要用**（`shadows-shipped-ui`，会顶掉官方控件）：

| 槽位 | 现状 |
|---|---|
| `shell.bottom` | 吃三栏高度 |
| `shell.leading` | 仅 `darwin && sidebarCollapsed` 挂载；现占 ui-sidebar 的展开 / 新建 |
| `sidebar.brand.mark` / `.brand.name` / `.toggle.badge` | 官方品牌标 / 展开按钮 |
| `conversation.session.header.corner` | 现占侧栏展开按钮 |

**session scope 的槽位**（`conversation.input.*`、`conversation.session.header.*`）
每个会话各渲染一份，全局动作放进去会重复 N 份。

### 4.4 桌面端的 HTTP 转发

`dsh-app://app` 下**非静态路径全部转发到 Host**，但代理会剥掉
`host / origin / cookie / sec-fetch-site`，再塞回自己的 cookie。

后果：插件的 HTTP 路由应挂 `ctx.connection.fetch.register`（它认得这种「无 Origin」形状），
`webServer.register` 只作源码模式兜底。

## 5. 会话连续性

- `session-persistence-jsonl` + `session-checkpoint-policy` 在 model request 前、top-level tool 前、每步前 flush
- 重载插件不动 session 服务 → **会话历史不丢**
- 但进行中的 turn / tool 会被中断，未落盘的工具结果按 `TOOL_OUTCOME_UNKNOWN` 恢复
- 现成积木：`agent.whenIdle()`、`agent.status 'idle'|'running'`、`jobs` status `running|stopping`、
  `hasDesktopActiveTasks(agents, jobs)` —— **均未被 HMR 使用**

## 6. 插件管理器

- `change()` 在 `hmr.runExclusive` 内 → `reload()` → `hmr.reconcileProfile`
- `ChangeResult.application` 默认 `'applied'`（有 hmr）；无 hmr 时 `'restart-required'` + `restartReason:'no-hmr'`
- `RestartReason = 'no-hmr' | 'package-moved' | 'host-module' | 'unmanaged-plugin' | 'module-comparison'`

**结论**：装 / 删 / 启停插件在桌面 profile 上本来就是热应用的，`restart-required` 很少见。
