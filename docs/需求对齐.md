# dsh-hot-restart — 需求对齐（第一轮，未写代码）

> 结论先行：**你的判断成立**。DSH 本身就内置了「热重置」能力（`ctx.hmr`），改插件不需要重启整个客户端；
> 「智能体杀自己进程」在 DSH 的进程模型下确实不合理，而且**技术上根本做不到优雅版**（见 §3）。
> 但有一处需要修正你的预期：**热重置本身也会打断正在跑的任务**（HMR 没有空闲等待，见 §4.1），
> 所以「智能体触发」这件事无论哪一档都只能「排程」，不能「当场执行」。
> 建议把功能拆成「热重置（默认、不碰进程）」和「整机重启（低频、外部执行）」两件事，而不是一件事的两种强度。
>
> **最终形态（经多轮讨论收敛）**：只做「配置热重置」。不碰进程、不做页面刷新、不做整机重启、
> **不做任何文件监听**、**零配置改动**。触发只有两个入口：智能体工具（同步返回结果）、用户点按钮。
> 「代码改完了没有」是语义判断，只有人/模型知道，文件系统判断不了——误触发会让插件变 `failed` 且不可逆。

## 1. 你的三个判断，逐条回应

| 你的判断 | 结论 | 依据 |
|---|---|---|
| 不想暴力杀进程 | 成立，而且没必要 | 热重置路径完全不碰进程；整机重启也有 `shutdown` → 10s 宽限 → SIGTERM → SIGKILL 的既有优雅链路，只是它由 Electron 主进程掌控 |
| 希望「热重置」：不关整个 desktop，只刷新所有 DSH 配置 | **DSH 原生支持**，这就是 `ctx.hmr.reconcileProfile()` | 见 §2 |
| 绝大多数情况不需要重开客户端 | 成立 | 见 §2.3 的「必须整机重启」清单；装/改插件默认就是 `application: 'applied'` |

## 2. DSH 里「热重置」到底是什么

### 2.1 核心能力：`ctx.hmr`

`@deepseek-ai/dsh-hmr` 提供 Host 服务 `ctx.hmr`，桌面 profile **默认已启用**
（`dsh-base` 的 patch 里 `disabled: !!js "!ctx.get('profileContext')"`，桌面端有 profileContext；
配置为 `root: []`，即只监听配置、不监听源码目录）。

三个关键方法：

| 方法 | 作用 |
|---|---|
| `reconcileProfile(requiredIds?)` | **热重置的全部内容**：按 profile manifest + patch 文件重新组合组合树，把「磁盘上文件变过的插件」停掉、重新 import、重新 apply。返回 `{ warnings, pending, restartReason }` |
| `runExclusive(operation)` | 与所有自动重载路径共用的串行队列。**必须在它里面调用 `reconcileProfile`**，否则会和文件监听/插件管理器打架 |
| `watchConfig(filename, refresh)` | 注册配置监听（我们大概率用不上，已有监听足够） |

一次 `reconcileProfile` 会覆盖：

- `cordis.patch.yml`（profile 的 patch 层）、home patch、profile `package.json` 的 `dsh.profile.bundles` 列表
- profile `node_modules` 下**已安装包**，以及 **`link:` 包的目标目录**——文件变了就替换
- 插件条目增删、启停、配置变更（走普通 Loader 条目更新）
- 完成后发出 `app-boot/config-reload` 事件（不带 diff，监听者自行重读 Loader）

> 这条对「开发 DSH 插件」尤其关键：用 `dsh plugin add link:<你的仓库>` 装进去，改源码 → 触发一次
> `reconcileProfile` → 新代码就在跑，**不需要重启**。

### 2.2 浏览器半边：`dsh-client-hmr`

`dsh-web-app` 里 `id: client-hmr` 常驻挂载（`pollIntervalMs: 500` 轮询各包 `lib/client.js` 的
mtime/ctime/size 作为 revision）。它做两件事：

- **插件图变化**（装/删/启停）→ 通过 `/plugins/events` SSE 推 `graph` 帧 → 浏览器自动增删插件，**无需刷页**
- **代码重建** → 推 `rebuilt` 帧 → 浏览器逐个替换插件 bundle

**关键点**：Host 侧那 500ms 轮询是**自己看文件**（mtime/ctime/size），不依赖谁去重建——
只要 bundle 文件变了，无论是不是 `dev:web` 写的，revision 都会推进、浏览器都会自动换。
真正需要 `location.reload()` 的只有一种情况：**Host release 变了**，
`ReleaseChangeGate` 会暂停插件更新直到页面刷新。

`release` 的构成（`dsh-client-modules/lib/index.js`）：

```js
const { version } = createRequire(import.meta.url)("../package.json")  // 0.2.1-rc.3
const commit = "be72761"                                                // 构建时固化
this.release = { version, commit }
```

**只在三类情况变化**：① 桌面端升级到新版本；② 换了一份 DSH 安装（commit 不同）；
③ 源码模式下换 checkout / 重新构建 Host。
**不会**因为它变：插件版本变化、插件文件改动、profile 配置改动、装/删插件。

### 2.3 三套监听，别搞混

| 监听 | 监听对象 | 默认状态 | 触发后 |
|---|---|---|---|
| **配置监听**（`watchConfig`，chokidar） | profile 的 `cordis.patch.yml` + `$DSH_HOME/cordis.patch.yml` + profile `package.json` | **常开**（HMR 启用即有） | `reconcileProfile()` |
| **模块源码监听**（`config.root`，chokidar） | `baseDir`（= profile 目录）下的 glob，默认 `ignored: ["**/node_modules", ...]` | **关闭**（`root: []`） | `partialReload()`（模块级热替换） |
| **client bundle 轮询**（`dsh-client-hmr`） | 各包 `lib/client.js` 的 `mtime/ctime/size` | **常开** | SSE 推 `rebuilt` → 浏览器就地替换 |

**所以「新加插件自动出现」是配置监听的效果**（profile `package.json` 的 bundles 列表变了）。

**`root: ["."]` 对本场景无效**，两个原因：

1. `baseDir = fileURLToPath(new URL(config.base || ".", ctx.baseUrl))`，而 `ctx.baseUrl` 是
   **profile 目录**；`link:` 开发包的目标在 profile 目录**之外**（如 `E:\Project\my-plugin`），不在 watch 范围；
2. 即便在范围内，默认 `ignored` 含 `**/node_modules`。

**真正让 `link:` 开发包生效的是 `reconcileProfile` 里的文件比较，与 watcher 无关**：

```js
// 比较范围 = profile 目录 + node_modules 下所有符号链接的目标
function profileRoots(dir) {
  const linked = readdirSync(modules).flatMap(...).filter(p => lstatSync(p).isSymbolicLink())
  return [dir, ...linked].map(root => root + sep)
}
// 比较键 = inode : size : mtimeMs
key: `${stats.ino}:${stats.size}:${stats.mtimeMs}`
```

官方 README 原话：「……会在下一次此类重新组合时生效，无需重启；**不要求通过 root 监听源码**」。

**缺的只是「什么时候调用」这个触发器**——本插件该做的是提供触发器，而不是实现模块监听。

### 2.4 热重置**做不到**的，只有这几类

`reconcileProfile` 的返回值已经把边界说清楚了：

| 情况 | 返回值标记 | 说明 |
|---|---|---|
| 改了 **宿主依赖图**里的模块（`dsh-app-boot`、Cordis、Loader 等） | `pending: [{reason:'host-module'}]` → `restartReason` | 这些模块被静态链接进进程入口，只能换进程 |
| profile 的 `node_modules` 里有指向开发 checkout 的符号链接，把宿主模块拉进比较范围 | `pending: [{reason:'module-comparison'}]` | 之后 Plugin Manager 会一直报 `restart-required`，直到重启 |
| runtime resolution 拒绝了发布（例如保留 profile 映射被移走） | `restartReason: 'package-moved'` | |
| 改了 `hmr` 这一行本身 | —— | 比较记录属于 hmr 实例，重启 hmr 会重新记录当前文件 |
| 在 Loader 树之外注册的插件 | `pending: [{reason:'unmanaged-plugin'}]` | |
| **Electron 主进程侧**（preload、托盘、窗口、协议） | 完全在 Host 之外 | 只能重开客户端 |
| 只改 `package.json`（不涉及文件内容） | 不检测 | 文档明确的限制 |
| 打包 worker loader / 已存在的 Worker、TSX 线程 | 不替换 | |

**结论**：改插件源码、改配置、装/删插件 → 热重置够用；改宿主依赖、改主进程壳 → 必须整机重启。
这个分界和你的直觉一致。

## 3. 为什么「让智能体杀自己的进程」不合理（也不可行）

我读了桌面壳的实现，这里有硬约束，不是设计口味问题：

1. **进程拓扑**：Electron 主进程 `spawn` 出 Host 子进程（`dsh-desktop-host/lib/index.js`，`stdio: [ignore, pipe, pipe, ipc]`），
   智能体跑在 Host 里。主进程一死 Host 跟着死（Host 侧还注册了 `process.once('disconnect')` → 主动 shutdown）。
2. **没有「请重启」的通道**：桌面壳的 IPC 通道表（`preload-app.cjs` 的 `DESKTOP_IPC`）里
   **没有任何 restart / relaunch / reload 通道**；`createProductApi()` 只暴露
   `browser / deviceInfo / keyboard / shortcuts / updates`。Host → 主进程的 `process.send`
   也只认 `ready / platform-session / shutdown-complete / fatal` 和 control 应答，
   未知 type 会被当作 control 响应丢弃。**插件无法请求 `app.relaunch()`**
   （`app.relaunch()` 只在 `!app.isPackaged` 的开发菜单和崩溃恢复对话框里可达）。
3. **Host 自杀 = 崩溃**：Host 退出时主进程走 `child.once('close')` → `fail()` → `reportFatal()`，
   弹出「应用无法启动或已意外停止」的恢复对话框（里面有「重启」按钮，但要**用户点**）。
   也就是说智能体自杀换来的不是重启，是一个错误弹窗。
4. **优雅关闭的开关在主进程手里**：`{type:'shutdown'}` 由主进程发给 Host，Host 执行
   `application.shutdown.shutdown(0)` → 回 `shutdown-complete` → 主进程等 10s → SIGTERM → 再 5s → SIGKILL。
   另有 `quit-inspection`（报告 `activeTasks` / `scheduledTasks`）和 `update-tasks`
   （`inspect | lock | unlock`，lock 会拒绝新请求、排空在途请求再复查）。
   **这套「先问有没有在跑的任务」的机制只存在于主进程侧，插件够不到。**
   桌面壳自己也因此有「关闭窗口 = 隐藏到托盘 + 提示任务继续」的行为。

所以正确形态是：**智能体只负责「排程」，执行交给外部**。这也是社区成熟插件的共同结论
（`dsh-autorestart` 用 detached helper + 双闸空闲检查；`dsh-reloader` 用 WMI
`Win32_Process.Create` 拉起脱离 job object 的 `restart.ps1`）。

### 3.1 智能体触发时，正在生成的内容怎么办

- 会话日志是持久化的（`sessionPersistence`），Host 死了不丢历史。
- 但**当前 turn 一定断**，工具调用结果可能来不及落盘。
- 所以不能「当场执行」，只能「排程 + 空闲窗口 + 重启后自动续跑」：
  1. 工具调用立刻返回「已排程 + 计划 + 预计影响」；
  2. 当前 turn 正常收尾（模型写完最后一条消息）；
  3. Host 侧等 `agents.list()` 全部 idle、`jobs` 无 running/stopping、无子代理在跑，再等一个静默窗；
  4. 外部助手执行重启；
  5. 重启后按落盘的重启记录给原会话投递一条续跑消息。

  注意：**目标会话如果自己有 goal 在驱动，就永远不会 idle**，需要先 disarm goal、重启后 re-arm
  （`dsh-autorestart` 踩过这个坑）。

## 4. 推荐的产品形态：三档动作，而不是一个「重启」

| 档位 | 名称 | 做什么 | 代价 | 触发者 |
|---|---|---|---|---|
| **L1** | 配置热重置 | `hmr.runExclusive(() => hmr.reconcileProfile())` | 无进程影响；**被替换的插件实例状态清零**；会话/工作区/job 保留 | 智能体工具 + UI 按钮 |
| **L2** | 页面刷新 | `location.reload()` | 页面闪一下，UI 局部状态丢失，设置面板会关 | UI 按钮（一般不需要） |
| **L3** | 整机重启 | 排程 → 空闲窗口 → 外部助手优雅重启 → 自动续跑 | 窗口消失几秒，当前 turn 断 | 只建议 UI 按钮 + 明确确认；智能体最多「排程」 |

**v1 建议只做 L1**（外加一个可选的「刷新页面」小按钮）。

理由：

- L1 覆盖「开发插件验证改动」这个真实场景的绝大部分。
- **L2 日常并不需要**：client bundle 的重建由 Host 侧 500ms 轮询自行发现并推给浏览器就地替换，
  只有 Host release（版本/commit）变化时 `ReleaseChangeGate` 才会要求刷页。
- L3 的复杂度（外部助手、空闲判定、续跑、回滚）远大于收益，做错就是「杀了服务起不来」。

> 值得强调：`pluginManager` 在桌面 profile 上装/删/启停插件**本来就是热应用的**
> （`ChangeResult.application === 'applied'`），只有 `restart-required` 时才需要 L3。
> 所以 L3 的真实使用频率会非常低——这进一步支持「v1 不做」。

### 4.1 ⚠️ L1 会打断正在跑的任务（但不会杀进程）

**HMR 没有空闲等待**。`reconcileProfile` 会直接 `fiber.await()` 停掉受影响插件——
`whenIdle` / `agents` / `jobs` 在 hmr 与 plugin-manager 的实现里命中 **0 次**。

**影响面比想象中窄**（`reconcileProfile` 只停「文件变了的那个插件」的 fiber，不是全局重启）：

| 部分 | 是否受影响 | 说明 |
|---|---|---|
| 会话日志 | ❌ 安全 | durable；`session-checkpoint-policy` 在 model request 前 / 每个 tool 前 / 每步前 flush |
| 其他插件、其他会话 | ❌ 安全 | 只停受影响插件的 fiber |
| 工作区 / job 记录 / UI 布局 | ❌ 安全 | 不涉及 |
| 正在执行的、**属于被替换插件**的 tool call | ⚠️ 中断 | 结果记 `TOOL_OUTCOME_UNKNOWN`，模型看到「结果未知」，可重试 |
| 被替换插件的**内存状态** | ⚠️ 丢失 | 需自行落盘 |
| 被替换插件的 **React 状态** | ⚠️ 丢失 | 需自行落盘/重建 |

**唯一「不可逆」风险**：替换版本加载失败 → 旧代码不再运行，插件变 `failed`。
修好文件后，下次重载会自动再导入（`reconcileProfile` 每次都会重试此前失败的导入），
但期间该插件不可用。建议：重载前记录「上一版是否可用」，失败时 UI 显示错误 + 一键再次重载。

### 4.2 触发策略：立即执行，只留一次确认

**「安全」的精确边界**：

| 「安全」成立的 | 「安全」不成立的 |
|---|---|
| 不杀进程、不杀 job、不杀 terminal | **替换版本加载失败 → 插件变 `failed`，旧代码不再运行** |
| 不丢会话历史、不丢文件 | 被替换插件的内存状态丢失 |
| 不重启 DSH、不影响其他插件/会话 | 被替换插件正在执行的 tool call 中断 |

| 触发者 | 行为 |
|---|---|
| **智能体工具** | **立即同步执行**，当场返回真实结果（见 §5） |
| **UI 按钮** | 弹**一次**确认框「重新加载所有已变更的插件？」→ **[重载] / [取消]**，点「重载」立即执行 |

### 4.3 为什么不做「稍后」（等空闲）

「稍后」= 等所有 agent idle 且无 running job。它要解决的问题，重载本身已经不构成问题：

| 之前担心的 | 实际 |
|---|---|
| job 会被杀 | ❌ 不会，job 归 agent 不归插件 |
| terminal 会被杀 | ❌ 不会，同上 |
| 别的会话被打断 | ❌ 不会，只停被替换插件的 fiber |
| 会话历史丢 | ❌ 不会，checkpoint 每步都 flush |

**唯一真会中断的**：正在执行的、**属于被替换插件**的 tool call。这种情况用「取消 → 等会儿再点」就够，
不需要维护「待执行排程 + 取消 + 恢复」的状态机。

另外两个理由说明「稍后」不可靠：

1. **有 goal 驱动的会话永远不会 idle**——「稍后」可能永远等不到；
2. 用户下一条消息又变「忙」——「稍后」可能无限期推迟。

**保留确认框**（按钮就在设置旁边，防误点），**去掉「稍后」**。

## 5. 智能体侧接口

只有一个工具，**立即同步执行、当场返回真实结果**：

```
dsh_hot_reload()
→ {
    applied: true,
    replacedPlugins: ["dsh-hot-restart", "dsh-pet"],
    pending: [{ url: "file:///.../dsh-app-boot/lib/index.js", reason: "host-module" }],
    restartReason: null,
    warnings: []
  }
```

不做「在飞任务清单」、不做「排程」、不加 `dsh_hot_reload_status()`。理由：

- **在飞任务清单是无效信息**：job / terminal 归 agent 不归插件（见 §5.1），
  重载不会杀它们；又无法把任务归因到具体插件，所以这份清单对模型没有可操作性，只是噪音。
- **排程会拖长链路**：把一次调用变成「先返回计划、下一轮再读结果」，
  而它要防的只是「本插件被替换导致响应丢失」这个罕见边角（见 §5.2）。
- **立即返回真实结果**，模型拿到就能直接汇报，不需要第二轮。

### 5.1 能力边界：任务无法归因到插件

| 能拿到 | 来源 |
|---|---|
| 哪些 agent 在跑 | `ctx.agents.list()` → `status` |
| 哪些 job 在跑（id / label / 状态） | `ctx.jobs.list()` |
| 哪些 terminal 还开着 | `ctx.terminals.list()` |
| **哪些插件被替换了**（事后） | `hmr/reload` 事件的 `reloads: Map<Plugin, Reload>` |
| **哪些插件将被替换**（事前） | ❌ 拿不到——比较记录是 `hmr` 实例的私有 `ModuleFiles.records` |

**任务不归插件所有**：`dsh-jobs` 里 `runningJobs(registry, owner)` 的 `owner` 是 **sessionId**，
`ensureOwnerCleanup(owner)` 也绑在 **agent** 生命周期上；terminal 同样是 `spawn(owner: Agent, …)`。
`ToolDefinition` 里也没有「注册者插件」字段。

### 5.2 job / terminal 不会被重载杀掉

因为归 agent 而非插件：

- **重载插件 → job 继续跑、terminal 继续开**，且仍可通过 `ctx.jobs.list()/kill()` 控制
- 真正随插件消失的只有：插件自己 `ctx.subprocess.spawn` 的子进程、它的内存状态

**唯一边角**：如果这次重载恰好把**本插件自己**替换掉，工具响应可能丢（模型看到「结果未知」）。
但重载确实发生，结果已落盘。只有开发本插件自己时才会遇到。

**为什么可以立即执行**（已核对 `dsh-tools` 链路）：`dispatchToolBody` 在 dispatch 时才
`resolveExecution(name)` 并 `await tool.execute(...)`；fiber dispose 只是从注册表移除，
**不会取消已捕获的调用**；结果处理（`postExecute` / `contentProjectors`）属于 `ToolRuntime` 服务，
也不受插件替换影响。

### 5.3 设计要点

- **必须把 `pending` / `restartReason` / `warnings` 原样返回给模型**。否则模型会以为「已生效」，
  用户看到的是旧行为，排查成本极高。这是社区插件最常见的坑。
- **工具描述里必须写清「有 `pending` 就需要整机重启」**。
- 结果同时落盘（`$DSH_HOME/dsh-hot-restart/state.json`），UI 轮询读；
  这样即使响应丢了（本插件被替换），UI 仍能看到结果。

## 6. 源码监听：不做（已决策）

**不做任何文件监听**。理由：

1. **「代码写完了」是语义判断，文件系统没有这个信息。** 静默窗只能判断「文件不再变化」，
   无法判断「代码写完了」——构建成功但逻辑没写完、保存了还没想好，都会误触发。
2. **误触发的代价不可逆。** `reconcileProfile` 遇到加载失败的替换版本时，
   **旧代码不再运行、插件变 `failed`**，直到文件修好才能恢复。半成品文件被加载 = 当场把环境搞坏。
3. **只有写代码的人（或模型）知道什么时候改完。** 所以触发权交给显式动作。

因此以下设计全部撤销：源码目录监听、debounce、静默窗、自激循环处理。

**触发方式只有两个**：

| 触发者 | 动作 |
|---|---|
| 智能体 | 调用 `dsh_hot_reload()` |
| 用户 | 点侧边栏按钮 / 设置页那一行 |

> 注：DSH 自带的两种「自动」仍然生效，与本节无关——
> ①配置监听（改 `cordis.patch.yml` / profile `package.json` → 自动 reconcile，这就是「新加插件自动出现」的原因）；
> ②`dsh-client-hmr` 每 500ms 轮询 `lib/client.js` → 浏览器就地替换 client bundle。

## 8. 已知风险与边界（要在 UI 里如实告知）

1. **热重置会替换本插件自己** —— 内存状态清零，必须落盘。
2. **HMR 不等空闲** —— 重载会打断受影响插件正在执行的 tool call，未落盘的工具结果按
   `TOOL_OUTCOME_UNKNOWN` 恢复（会话历史本身不丢）。所以工具要排程而非当场执行。
3. **`link:` 开发包可能把宿主模块拉进比较范围** —— 之后会一直 `restart-required`；
   如果开发的插件依赖很重，可能反而需要重启。UI 要能展示这个原因。
4. **只改 `package.json` 不会被检测** —— 需要重启或触发一次重组合。
5. **桌面代理会剥掉 `Origin`/`Host`**（`forwardWebRequest` 删 `host/origin/cookie/sec-fetch-site`，
   再塞回自己的 cookie）—— 插件 HTTP 路由建议 `ctx.connection.fetch.register` 与
   `ctx.webServer.register` 双挂，前端先探 `/ping` 再选通道；写操作要有同源/回环校验。
6. **Host release 变化时需要刷页** —— `ReleaseChangeGate` 会暂停插件更新。
   但这是 DSH 升级场景，页面自己会弹提示并提供刷新按钮，本插件不需要做 L2。
7. **替换版本加载失败后旧代码不再运行** —— 插件变 `failed`，修好文件后下次重载会重新导入，
   期间该插件不可用。UI 要明确显示。

## 9. 已确认的决策

| 项 | 决策 |
|---|---|
| L1 配置热重置 | ✅ 做 |
| L2 页面刷新 | ❌ 不做（client bundle 由 Host 轮询自动替换；release 变化时页面自己会提示） |
| L3 整机重启 | ❌ 不做（「关掉再打开」不值得为它写外部重启器） |
| **智能体触发** | **立即同步执行**，当场返回真实结果（不排程、不返回在飞任务清单） |
| **UI 触发** | 弹一次确认框「重新加载所有已变更的插件？」→ **[重载] / [取消]**，点「重载」立即执行 |
| **「稍后」（等空闲）** | ❌ 不做（job/terminal 不会被杀，等空闲无必要且不可靠） |
| UI 入口 | `sidebar.footer.action`(order 10) + `settings.general.item`(order 110) |
| **源码目录监听** | ❌ **完全不做**（「代码改完」是语义判断，误触发不可逆） |
| **静默窗 / debounce** | ❌ 不需要（没有监听就没有这个问题） |
| **自激循环** | ❌ 不存在（没有监听就不会自激） |
| 触发方式 | **只有两个**：智能体调工具、用户点按钮 |
| **配置改动** | **零**——不动 `hmr`、不动 `root`、DSH 自带的两套自动行为保持原样 |
| `hmr` 的 `root` | 保持 `[]` |

## 附录：证据（本次勘察确认过的事实）

**Host / HMR**

- `ctx.hmr` = `@deepseek-ai/dsh-hmr`。`runExclusive`（lib/index.js:748-756）= AsyncLocalStorage 串行队列，
  禁止嵌套、关闭后拒绝。`reconcileProfile`（L1320-1385）必须在 `runExclusive` 内（L1321）。
- 比较基准 = 临时标记文件 mtime（`files.now()`）；比较范围 = profile 目录 + `node_modules` 下符号链接目标；
  比较键 = `inode:size:mtimeMs`（`identityOf` L408-419）。
- `planReplacement`（L1214）：落在 host 静态图 → `pending[{reason:'host-module'}]`；
  非 Loader entry 的插件 → `pending[{reason:'unmanaged-plugin'}]`；其余 evict（L1157 清 ESM `loadCache` + CJS `require.cache`）
  → `stopPlanned`（L1274：manifest 失效、evict、registry.delete、`fiber.await`）→ app-boot `recomposeProfile`（L3782）重启 entry。
- `restartReason` 只有两种：`'module-comparison'`（比较失败或无 ESM cache，L1363）、
  `'package-moved'`（app-boot L3840-3845 的 `ResolutionRestartRequired`）。
  `pluginManager` 上报 `restartReason ?? pending[0].reason`（L2367）。
- HMR 里 `whenIdle` / `agents` / `jobs` 命中 **0 次**——没有任何空闲等待，直接 `fiber.await()`。

**桌面壳**

- Electron 主进程 `spawn` Host：`main.js:3794`，`stdio: [ignore, pipe, pipe, ipc]`。
- `desktop-runtime.json` = 打包清单（release/platform/arch/sharedPackages/files+sha256），main.js:103-127 校验。
- `dsh-desktop-host/lib/index.js`：`process.on('message')` 只处理 `shutdown / quit-inspection / update-tasks(inspect|lock|unlock)`；
  另有 `hasDesktopActiveTasks()`、`installDesktopQuitInspection()`、`installDesktopUpdateTaskControl()`。
- `host.stop()`（main.js:3910）：发 `{type:'shutdown'}` → 等 10s → SIGTERM → 再 5s → SIGKILL。
- `app.quit()` → `before-quit`（L13094）preventDefault → `quitConfirmation.confirm()` →
  `host.inspectQuit()`（L3870，返回 `activeTasks`/`scheduledTasks`）→ 有任务弹原生框 → `finishQuit`（L13069）。
- 关窗 = 隐藏到托盘（L12894-12906，首次弹 `background-close-confirmed` 提示）；托盘菜单「退出」→ `app.quit()`。

- `preload-app.cjs`：`DESKTOP_IPC` 全表**无** restart/relaunch/reload 通道；`createProductApi()` 只有
  `browser / deviceInfo / keyboard / shortcuts / updates`。

- 单实例锁 `claimDesktopSingleInstance`（L7659）：第二个实例退出并聚焦第一个。

**客户端**

- `dsh-client-hmr` host 侧 500ms 轮询 bundle `mtime/ctime/size` → `clientModules.rebuilt(id)` → SSE `/plugins/events`

- `session-persistence-jsonl` + `session-checkpoint-policy` 在 model request 前、top-level tool 前、每步前 flush

**插件管理器**

**配置启用状态与三套监听**

- `dsh-base/cordis.patch.yml`：`- id: hmr / name: '@deepseek-ai/dsh-hmr' / disabled: !!js "!ctx.get('profileContext')" / config: { root: [] }`
  —— 桌面端有 profileContext，**默认启用**；`root: []` 表示**不监听模块源码目录**。
- `dsh-web-app/cordis.patch.yml`：`- id: client-hmr / name: '@deepseek-ai/dsh-client-hmr'`（常驻）。
- **配置监听（常开）**：`const patchFiles = [profile.patchPath, join(profile.home, PROFILE_PATCH_FILENAME)]`
  → `watchConfig(profile.patchPath)` + `watchConfig($DSH_HOME/cordis.patch.yml)` + `watchConfig(profile/package.json)`。
  回调 `refresh()` 读 bundles 列表与 patch 文本做 diff，变了才 `reconcileProfile()`。
  **这就是「新加插件自动出现」的原因。**
- **模块源码监听（默认关闭）**：`this.baseDir = fileURLToPath(new URL(config.base || ".", ctx.baseUrl))`，
  `ctx.baseUrl` = profile 目录；`ignored` 默认含 `**/node_modules`。`link:` 目标在 profile 之外 → **监听不到**。
- **`profileRoots(dir)`**（文件比较范围，与 watcher 无关）：
  `[profile.dir, ...node_modules 下所有符号链接的目标]`，两者都取 JS/native 两种 realpath 拼写。
- **`ModuleFiles.identityOf`**：`key = ${ino}:${size}:${mtimeMs}`；
  `compare()` 对无记录模块用 `modifiedAt >= observedAt - 2000ms` 判定。
- **`profileModules(roots)`**：`[...this.loadedUrls()].filter(url => roots.some(root => filename.startsWith(root)))`。

**linkedRoots（开发包目录的权威来源）**

- `dsh-app-boot/lib/index.js` 的 `linkedProfileRoots(profile, profilesDir)`：
  扫描 `profile/node_modules` 下所有符号链接，`realpath` 后**排除** `profiles/` 自身与 profile 目录内的链接，
  返回 `[{ name: <相对 node_modules 的包名>, realPath }]`，按 name 排序。
- 该数组挂在 `ctx.get('pluginPackages')?.resolution?.linkedRoots`（`PluginPackages` 服务，`scope: 'profile'` 的条目同表）。
- `mappedDirectories(resolution)` 把它与 `entries.filter(scope==='profile')` 的 `packageDir` 合并成「profile 映射目录集」。
