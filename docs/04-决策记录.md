## 1. 整机重启的先后三个方案

| 方案 | 做法 | 结论 |
|---|---|---|
| 早期「L3」 | 两段式确认 → 等所有 agent idle（先 disarm goal）→ 外部助手 → 重启后 resume 会话 | ❌ 复杂度远大于收益；有 goal 的会话永不 idle；做错就是「杀了服务起不来」 |
| 纯 PowerShell 助手 | `spawn('pwsh', [...])` 起脚本 | ❌ 曾误以为必需（job object 误判），实际 detached spawn 就够 |
| WMI `Win32_Process.Create` | 用 WMI 创建脱离 job 的进程 | ❌ **已否决**：DSH 进程树根本不在 job object 内（实测 `NO_JOB`），不需要 WMI |
| **采用：Node `spawn({detached:true})`** | 用自带 `node.exe` 跑 `.mjs` 重启器 | ✅ 零外部依赖、失败面最小 |

> WMI 那条的否决依据见 [02-平台事实.md §3.2](02-平台事实.md) —— 那是一个测量陷阱导致的错误结论。

## 2. 源码目录监听（曾完整设计，后完全撤销）

| 方案 | 否决原因 |
|---|---|
| 开启 `hmr` 的 `root: ["."]` | 监听不到 `link:` 包（在 profile 之外），且 `ignored` 含 `**/node_modules`；只剩误触发风险 |
| 本插件自己监听 `linkedRoots` 的 `lib/**/*.js` | **核心否决**：「代码写完了」是语义判断，文件系统判断不了 |
| debounce 300ms + 静默窗 800ms | 撤销监听后一并取消 |
| 自激循环处理（跳过自身目录） | 撤销监听后不存在此问题 |

### 2.1 为什么「静默窗」救不了

静默窗只能判断「文件不再变化」，**无法判断「代码写完了」**。

而 `reconcileProfile` 遇到加载失败的替换版本时：

> **旧代码不再运行，插件变 `failed`，直到文件修好才能恢复。**

所以「保存到一半 → 半成品被加载 → 插件当场变 `failed` → 原来的好版本也没了」。
这个后果**不可逆**，不能靠调参规避。

**结论**：「改完了没有」只有写代码的人（或模型）知道，触发权必须交给显式动作。

## 3. 页面刷新（L2）

| 方案 | 否决原因 |
|---|---|
| 提供 `location.reload()` 按钮 | client bundle 由 `dsh-client-hmr` 轮询自行替换，日常不需要；Host release 变化时页面自己会提示 |
| 重启后轮询 `/ping` + 自动 `location.reload()` | **做不到**：杀掉主进程时窗口一起消失，不存在「活着的页面在等新实例」 |

## 4. 智能体触发的排程策略

| 策略 | 结论 |
|---|---|
| **A：本轮收尾后执行** | 曾采用，后改为「立即同步执行」——避免把单次调用变成两步；它要防的只是「本插件被替换导致响应丢失」这个罕见边角 |
| **B：等所有 agent idle** | ❌ 智能体触发时自己正在跑，当场不成立；等到时本轮已结束无法汇报；有 goal 的会话永不 idle；用户发下一条消息又变忙 |
| **C：用户确认** | UI 场景才适用；后简化为「两个按钮 + 条件确认框」 |
| **采用：立即同步执行** | 返回真实结果，模型拿到即可汇报 |

## 5. 「稍后」（等空闲）重启

**否决**：job / terminal 归 agent 不归插件，重载不会杀它们；且等空闲不可靠（goal / 新消息）。
改为「有任务就**禁止**重启」的硬策略——安全优先。

---

## 6. 把「在飞任务清单」返回给模型

**否决**：无法把任务归因到具体插件（`ModuleFiles.records` 是 hmr 私有字段；job owner 是 sessionId）。
该清单对模型没有可操作性，只是噪音。

**但 UI 的提示框需要它** —— 所以保留在 `inspectActivity()` 里，只给 UI 用。

## 8. 设置入口的其他候选

| 槽位 | 否决原因 |
|---|---|
| `settings.section`（独立一页） | 用户明确要「通用页最后一行」，不是独立导航页 |
| `plugins.detail.actions` / `plugins.detail.section` | 语境贴合，但用户未选；可作为后续加分项 |
| `conversation.session.header.utilities` | 与第三方插件抢位，窄屏要折叠 |
| `conversation.input.left` / `input.right` | 高频但冲突风险高（`dsh-reset-button` 已占 `input.right`） |
| 托盘菜单 | 托盘在主进程侧，插件够不到 |

### 8.1 迭代 2：入口从「通用设置」迁到插件详情页

| 方案 | 结论 |
|---|---|
| 留在 `settings.general.item` | ❌ 通用页放的是**全局偏好**（语言、主题、输入框回车），而热重载 / 重启是**本插件自己的动作**，语境不对 |
| `plugins.detail.section` | ⭕ 可行（总渲染，组件自己判断 subject），但它是「详情页下方追加一段」，位置在组件行之后，不如 bundle 配置位自然 |
| **采用：`plugins.bundle.config`，key = 包名** | ✅ 宿主专门留给「bundle 自己的配置」，位置在描述与组件行之间，正是用户看这个插件的地方 |

用户选择：插件页内保留「侧边栏开关 + 热重载按钮 + 重启客户端按钮」，
**通用设置里那一行整行移除**。

> 硬约束：`key` 必须精确等于包名 `dsh-reload`。插件页用
> `ledger.bundles.has(pkg.name)` 判断是否渲染，写成 Loader entry id 会静默不显示。

### 8.2 迭代 3：「通用设置」彻底清空，新增设置面板顶栏入口

用户反馈：通用页不该再有任何本插件内容（连「在侧边栏显示热重载按钮」那个开关
也不该在那儿），并要求在「账户与余额」页最下方靠右下放两个按钮。

**第一步：通用页全部撤掉**（已执行）

| 撤掉的东西 | 原因 |
|---|---|
| 「热重载 / 重启客户端」两个按钮那一行 | 通用页是全局偏好的座位，不是动作面板 |
| 「在侧边栏显示热重载按钮」开关 | 它属于本插件的偏好，应在本插件自己的页 |
| 「在通用设置里显示…」开关 | 它控制的东西已经不存在了，留着是无意义的中转 |

结果：`settings.general.item` 不再注册，`state.generalRowVisible` /
`PREF_GENERAL_KEY` / `GeneralSettingsRow` 全部删除。

**第二步：账户页右下角的落点**（已确认方案 A）

先查了宿主源码：`dsh-client-ui-settings-account` 的 `AccountSection` 内部
**`renderSlot` 调用数为 0** —— 账户页的 DOM 是宿主自己写死的，「最下方」那块
没有任何官方扩展点。所以「真·右下角」只能靠 DOM 定位 hack。

| 方案 | 结论 |
|---|---|
| **A. `settings.action`（官方槽位）** | ✅ **采用**。设置在面板顶栏右侧、Close 左边；root scope，任何设置页都在；零 hack |
| B. 自绘浮动条 + DOM 定位到右下角 | ❌ 要依赖宿主 CSS 类名与结构，DSH 升级后会静默失效或位置跑偏 |
| C. 只放插件详情页 | ❌ 用户明确要第二个更容易到达的入口 |

**方案 A 的代价（已如实告知用户并获确认）**：位置是**顶栏右侧**而不是页面底部。
换来的是稳定性——官方槽位不随宿主 DOM 结构变化而失效。

**顺带发现的宿主缺陷**：Windows 上侧边栏折叠时
`[data-windows-titlebar] .collapsed .footArea { display: none }` 会把
`sidebar.footer.action` 整块隐藏，而 `shell.leading` 只在 `darwin && sidebarCollapsed`
挂载，Windows 折叠后没有替代座位。**这正是需要第二个入口的硬理由。**

## 10. 重启失败兜底

| 方案 | 结论 |
|---|---|
| 自动回滚到上一可用版本 | ❌ 需要备份插件文件；`link:` 包回滚意义不大 |
| 写诊断报告 + 下次启动提示 | ❌ 第一版不做 |
| **采用：只做客户端 8 秒超时解锁** | ✅ 不是兜底，只是防止 UI 永久冻结 |

### 10.1 补充（迭代 2）：拉起新实例必须剥离 Electron-as-node 环境

| 方案 | 结论 |
|---|---|
| `spawn(exe, [], { env: {...process.env} })` | ❌ **这就是 bug 本身**：Host 环境带 `ELECTRON_RUN_AS_NODE=1`，新实例变成纯 Node 进程、不建窗口、秒退 |
| 清空环境只留 PATH | ❌ 会丢掉 `DSH_HOME`、代理等用户环境，新实例行为可能不一致 |
| **采用：`desktopLaunchEnv()` 精确删三个变量** | ✅ 只删让 Electron 退化成 Node 的开关，其余原样保留 |
| 只靠 `spawn()` 判断成功 | ❌ 静默失败：秒退也是 exit 0 |
| **采用：拉起后观察 ~2s 存活 + 重试 3 次** | ✅ 把「起来了」和「活下来了」区分开；单实例锁释放有延迟，重试能救回来 |

**教训**：这条链路的两段失败（锁未释放、环境变量残留）都是**零错误信息**的。
凡是「子进程自己悄悄退出」的场景，都不能只看 `spawn()` 的返回值。

## 11. `parameters` 与 `output.schema` 的设计取舍

| 方案 | 结论 |
|---|---|
| 工具带参数（如 `when: 'now'` / `dryRun`） | ❌ 第一版不需要：模型想「立刻」直接调就行 |
| 第二个工具 `dsh_hot_reload_status()` | ❌ 结果已落盘 + UI 展示，再加工具是冗余 |
| 输出只返回 `applied/changed/replacedPlugins` | ❌ 少了 `pending` / `restartReason` 会让模型误以为「已生效」 |
| **采用：8 字段完整输出 + `notes` 中文摘要** | ✅ 模型能如实汇报，用户也能看懂 |
